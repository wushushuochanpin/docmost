## 模型扩展：基于现有 JSON/Meta 字段延伸

在文档实体（`Document` 机结构或相关模型）中，不建议直接向关系型数据库中做 DDL 增加具体的 `theme_color_column` 字段。
而是倾向于将布局排版属性直接塞入已被广泛持有的 JSONB 特性配置表或 `properties` / `meta` 字典中。

### 属性字段规范

需要在后端定义的模型约束中，许可以下字典 Keys：

| JSON 字段键 | 数据类型 | 可选枚举上限域 | 缺省默认值 | 释义 |
|---|---|---|---|---|
| `theme_color` | string / enum | `white`, `yellow`, `green`, `blue`, `pink` | `white` | 画布底色。基于语种独立渲染对应的色环基调。 |
| `theme_pattern` | string / enum | `blank`, `dots`, `grid`, `lines` | `blank` | 画布底纹图案。 |

## 数据迁移与兼容性 (Compatibility)

**1. 对存量老文档的影响：**
由于缺省值为 `white` 和 `blank`，对于历史数百万的未设置过背景数据的存量老文档，前后端拉取时，代码容错（如 `doc.properties?.theme_color || 'white'`）可确保渲染页面依然是白板，无需任何“刷全表、洗历史数据”的数据迁移回填脚本操作。完全的静默向前兼容。

**2. 预留未来的脏数据清洗机制 (Schema Validation)：**
由于直接写在 JSON 层，前端下发的数据极容易被篡改。应用服务后端层应对 `theme_color` 与 `theme_pattern` 这两个字段执行 Schema 的白名单 Enumerator 解析效验。若收到 `theme_color: "hacker_black"`，后端必须阻断报错（400 Bad Request），拒绝入库。
