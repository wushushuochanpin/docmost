# 03 数据模型与存储设计

**成文日期**：2026-04-08 13:46:11 UTC+8
**最后修订**：2026-04-08 13:46:11 UTC+8

本文档用于定义核心实体、字段与存储策略。阅读时当前系统实现可能已发生变化，请以实际代码与产品行为为准，谨慎参考。

---

## 设计原则

1. 复用现有表优先，避免新建平行知识存储。
2. 向量索引按 chunk 维度组织，便于长文档语义召回。
3. Token 治理优先补语义，而不是推翻现有认证表。
4. 首期尽量少做不可逆迁移，优先采用向后兼容改造。

## 现有核心表

| 表/结构 | 当前用途 | 本专题用途 |
| --- | --- | --- |
| `pages` | 页面主表，含 `text_content`、`tsv` | 作为正文 source of truth 与关键词召回基础 |
| `attachments` | 附件元数据与文件定位 | 后续可扩展为附件检索源 |
| `page_embeddings` | 向量索引与 chunk 元数据 | 作为语义召回基础 |
| `sc_api_tokens` | API Token 主表 | 作为 MCP/Bearer 鉴权与 scope 载体 |
| `sc_api_token_events` | Token 生命周期事件 | 用于 Token 创建/撤销留痕 |
| `sc_audit_events` | 审计事件 | 用于外部 AI 调用留痕 |

## 关键实体设计

### 1. `sc_api_tokens`

首期不更换表，只增强字段语义。

| 字段 | 当前状态 | 目标语义 |
| --- | --- | --- |
| `id` | 已存在 | Token 主键 |
| `tokenHash` | 已存在 | Bearer 明文哈希 |
| `scopeJson` | 已存在但当前默认为空数组 | 改为显式 scope 列表，首期至少支持 `knowledge.read` |
| `isWorkspaceManaged` | 已存在 | 区分个人/工作区级 Token |
| `lastUsedAt` | 已存在 | 记录最近一次 MCP/REST 使用时间 |
| `lastUsedIp` | 已存在 | 记录最近一次来源 IP |
| `expiresAt` | 已存在 | Token 到期时间 |

推荐 `scopeJson` 首期枚举：

```json
["knowledge.read"]
```

后续可扩展：

```json
["knowledge.read", "knowledge.write", "space.read"]
```

### 2. `page_embeddings`

当前类型已经具备：

- `pageId`
- `spaceId`
- `workspaceId`
- `embedding`
- `chunkIndex`
- `chunkStart`
- `chunkLength`
- `metadata`

本专题建议：

1. 继续复用 `page_embeddings` 作为统一的 chunk 级语义索引表。
2. `metadata` 中补充以下结构化字段：
   - `source_type`: `page`
   - `content_hash`
   - `page_title`
   - `page_url`
   - `chunk_preview`
   - `updated_at`
3. 若当前 `attachmentId` 强制非空影响 page chunk 写入，则在迁移中改为 nullable，避免通过占位值污染语义。

### 3. 检索结果对象

不强制建表，首期可由服务层实时组装：

```json
{
  "id": "page:uuid:chunk:3",
  "page_id": "uuid",
  "space_id": "uuid",
  "title": "文档标题",
  "snippet": "命中片段",
  "score": 0.87,
  "url": "/p/slug-or-share-link",
  "updated_at": "2026-04-08T00:00:00.000Z"
}
```

## 分块策略

1. 分块单位：优先按标题、段落、列表、代码块边界切分，而不是固定字符硬切。
2. 目标 chunk 长度：建议 500-1200 中文字符等价内容。
3. 重叠策略：相邻 chunk 保留有限 overlap，降低断句带来的上下文损失。
4. metadata 保留标题路径和 breadcrumb，便于在 `fetch` 阶段恢复定位。

## 索引更新策略

### 首期

1. 页面创建/更新后触发增量重建 embedding。
2. 工作区开启 `aiSearch` 时可对全量页面补建向量。
3. 页面删除或权限失效时，从向量结果中过滤或软删除。

### 后续

1. 附件、评论纳入统一检索时，按 `source_type` 扩展。
2. 支持 content hash 去重与局部重建。

## 迁移方案

### Migration 1：Token Scope 语义化

1. 保持 `sc_api_tokens` 表结构不变。
2. 为旧 Token 回填默认 `["knowledge.read"]` 或服务端按空数组解释为 `knowledge.read`。
3. 前端 Token 页面增加 scope 说明。

### Migration 2：Embedding 元数据增强

1. 保持 `page_embeddings` 为主表。
2. 新写入的 `metadata` 补充 `source_type/content_hash/page_url`。
3. 如 `attachmentId` 约束阻碍 page chunk 存储，则迁移为 nullable。

### Migration 3：审计增强

1. 首期不新增独立 MCP 审计表。
2. 通过现有审计表新增事件类型与 metadata 字段承载工具调用信息。

## 回滚方案

1. Token scope 如出现兼容性问题，可暂时把空数组解释为 `knowledge.read`，不阻断旧 Token。
2. embedding metadata 扩展如出现异常，可回退到仅用 FTS，不影响页面正文。
3. `attachmentId` nullable 迁移若触发兼容问题，可暂停写入 page chunk，仅保留已存在的 embedding 数据。
