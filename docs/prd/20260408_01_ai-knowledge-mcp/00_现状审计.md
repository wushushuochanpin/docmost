## 审计范围

- 审计目标：确认当前仓库是否已经具备“AI 可接入知识库”的底座，以及缺口位于哪一层
- 审计方法：以 `apps/server/src` 和 `apps/client/src` 的现有实现为准，优先判断认证、页面读取、检索、导出、MCP 预留与审计能力

## 已确认缺口

| 缺口 | 当前状态 | 风险 |
| --- | --- | --- |
| 真实 MCP 服务端 | 开源代码中未找到 `/mcp` controller/module/server 实现 | 前端文案可开、能力不可用，形成产品落差 |
| Token Scope | `scopeJson` 当前写入为空数组 | 无法精细区分只读检索与高风险写操作 |
| LLM 检索质量 | 当前搜索以 page-level FTS 为主 | 多段长文档召回、语义查询、跨段引用质量不足 |
| 工具暴露边界 | 前端文案列出大量工具，但缺少实际服务端注册与分阶段开放机制 | 如果直接开放 CRUD，风险高于收益 |
| 外部 AI 安全 | 现有审计可用，但未形成 MCP 级限流、只读审批策略、外部工具出参约束 | 容易出现越权调用、提示注入与数据外泄风险 |
| 深度研究兼容性 | 现有接口是业务 REST，不是 MCP `search/fetch` 协议形态 | 无法直接供 remote MCP 客户端复用 |

## 复用结论

1. 现有 REST 与 service 层足够作为知识访问内核，不应新建第二套内容数据库。
2. 现有 Token、Audit、Workspace 识别、Page Access、导出、Embedding 表结构均应优先复用。
3. 真正需要新增的是“协议适配层 + 检索编排层 + scope/限流/工具治理层”，不是重做整个内容管理系统。

## 关键风险

1. 如果跳过检索层设计，直接把现有页面 REST 包装成 MCP，AI 体验会很差，且难以控制写风险。
2. 如果只做 OpenAI vector store 同步而不做 MCP，则短期见效快，但无法满足多客户端复用、实时 ACL 和后续写回。
3. 如果首期就开放写工具，会在 scope、审批、审计、幂等未成型前把风险暴露到外部 AI。

## 审计结论

本仓库当前最合适的演进路线不是“从零造一个 AI 知识平台”，而是：

1. 以现有页面、搜索、导出、Token、Audit 为基础保留 Docmost 作为 source of truth。
2. 先补齐权限感知的检索与读取层。
3. 再在其上实现一个只读优先、跨客户端可复用的 remote MCP 薄适配层。
