## 背景

1. 当前仓库已经具备 API Token、页面读取、全文搜索、页面/空间导出、审计日志、AI Search 开关与 MCP 开关 UI 等基础能力，但开源代码中尚未落地可用的 `/mcp` 服务端实现。
2. 用户希望把当前在线文档项目作为个人知识库，供 ChatGPT、Cursor、Claude、Codex 等 AI 工具安全调用，目标不是一次性做完所有 AI 功能，而是先形成稳定、可治理、可扩展的知识接入层。
3. 结合现有代码与行业实践，本专题需要回答的核心问题不是“是否做 MCP”本身，而是“知识源、检索层、协议层、认证层”如何分层建设。

## 关键决策

1. 首期目标不是把所有现有 REST API 直接暴露给 AI，而是建设“权限感知的检索与读取层”。
2. 协议层采用 remote MCP，但必须是对现有能力的薄适配层，不新建平行知识库系统。
3. 首期仅交付只读工具，优先满足 `search + fetch` 两个核心能力；写入类工具延后到 scope、审批、审计、幂等机制齐备后再开放。
4. 首期认证沿用现有 Bearer API Key 体系；OAuth 兼容的远程 MCP 授权放入后续阶段。
5. 检索层采用 hybrid retrieval 路线：关键词召回保留现有 FTS，语义召回基于向量分块索引补齐，必要时再加入 rerank。
6. 不把“OpenAI vector store only”作为唯一正式方案；它可以是快速试运行选项，但不是跨客户端与实时权限场景下的主方案。

## 非目标

1. 不在首期开放页面创建、更新、移动、删除等写操作给外部 AI 工具。
2. 不在首期引入第三方 SaaS 作为唯一知识主存储，Docmost 仍然是 source of truth。
3. 不在首期解决全部导入源同步、外部知识融合、组织级 OAuth 联邦登录等扩展能力。
