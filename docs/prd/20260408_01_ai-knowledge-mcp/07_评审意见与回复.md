## 评审问题与回复

| review_id | 评审问题 | 回复 | 结论 |
| --- | --- | --- | --- |
| RV-001 | 为什么不直接把现有 REST API 暴露给 AI？ | 现有 REST 偏业务对象 CRUD，不是面向 LLM 的检索接口；直接暴露既影响体验，也会提前放大写风险。 | 采纳“检索层先行，协议层薄适配” |
| RV-002 | 为什么首期不直接做写工具？ | 当前 scope、审批、幂等、回滚尚未闭环，写工具风险明显高于收益。 | 采纳“首期只读” |
| RV-003 | 是否必须马上做 OAuth？ | 不是。首期可复用 Bearer API Key；但面向多客户端的长期方案应补 OAuth 兼容授权。 | 采纳“先 Bearer，后 OAuth” |
| RV-004 | 是否只做 OpenAI vector store 就够？ | 对单一客户端和快速验证够用，但无法满足跨客户端、实时 ACL、统一治理和未来写回。 | 采纳“vector store 仅作为快速方案，不是正式主方案” |
| RV-005 | 为什么要保留现有 FTS？ | FTS 成本低、回退快、对关键词查询有效，是向量索引不可用时的兜底路径。 | 采纳 hybrid retrieval |

## 待确认事项

1. 是否在首期就支持 `list_spaces` 等附加只读工具。
2. `page_embeddings.attachmentId` 是否需要做 nullable 迁移。
3. 是否在审计表中单独区分 MCP 与 REST 查询事件。

## 不采纳项

1. 不采纳“一页统一承载 MCP、Token、审计所有能力”的单页工作台设计。
2. 不采纳“跳过 scope 设计，默认所有 Token 都可写”的简化路线。
