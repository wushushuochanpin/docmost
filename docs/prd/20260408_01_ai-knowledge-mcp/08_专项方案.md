## 专项主题：知识接入方案选型

## 候选方案

### 方案 A：仅导出到 OpenAI vector stores / file_search

- 优点：
  - 落地最快
  - 对 OpenAI 生态友好
- 缺点：
  - 不适合多客户端复用
  - 实时 ACL 与实时内容同步复杂
  - 容易形成第二份知识副本

### 方案 B：直接把现有 REST 做 generic MCP 包装

- 优点：
  - 开发量看似最小
  - 可快速暴露大量工具
- 缺点：
  - 工具语义不适合 LLM
  - 写风险高
  - 检索质量差
  - 协议层与业务层耦合过重

### 方案 C：检索层 + remote MCP 薄适配层

- 优点：
  - 与现有系统复用度高
  - 可兼顾多客户端
  - 便于阶段化开放只读/写入
  - 有利于做 ACL、审计、限流
- 缺点：
  - 首期需要额外建设 retrieval orchestration

## 选型结论

选择方案 C 作为正式主路线，方案 A 作为快速试运行补充方案。

## 验收要求

1. 正式主路线必须支持跨客户端的 remote MCP。
2. 首期必须实现 `search + fetch`。
3. 正式方案必须依赖现有 Docmost 权限模型，而不是离线副本独立授权。
4. 正式方案必须允许关闭 MCP 后快速回退。

## 深度研究类客户端兼容要求

1. 首期至少提供 `search` 与 `fetch`。
2. `search` 返回的结果必须足够让模型选择下一步 `fetch`。
3. `fetch` 返回正文时优先 Markdown，而不是富文本 JSON。

## 质量专项

### 检索质量

1. 不满足于”搜得到页面标题”。
2. 必须返回片段与定位信息。
3. 向量检索不可用时仍可用 FTS 兜底。

### Token 成本专项

1. AI 客户端必须先 `search` 定位，再 `fetch` 读取，不允许默认拉取整库或整棵页面树。
2. `search` 默认只返回少量候选结果、标题、路径、片段、更新时间和稳定 ID。
3. `fetch` 默认返回 `section` 级内容，并受 `max_tokens` 约束；`full` 模式仅在用户明确要求或文档足够短时使用。
4. 下级文档/文件夹必须通过 `include_children=true` 显式开启，并受 `max_depth` 与服务端硬上限约束。
5. 图片默认返回 metadata；URL 与 base64 内联均必须按需启用，base64 必须有大小阈值与 fallback。

### 治理质量

1. Token 可撤销、可追踪、可限制。
2. 工具调用可审计。
3. 写工具默认关闭。

## 专项主题：接入协议选型（CLI 工具 vs remote MCP）

**决策日期**：2026-04-26

## 决策背景

本专项评估了两种协议接入方式：CLI 工具与 remote MCP 服务。目标场景是：外部用户将 AI 助手（Claude、Cursor、ChatGPT 等）接入自己的 Docmost 知识库，实现知识的实时查询与读取。

## 候选方案

### 方案 E：CLI 工具

- 描述：提供命令行工具，用户在本地执行 `search/fetch`，将输出喂给 AI 工具
- 优点：
  - 开发量小
  - 适合脚本化与批量处理
  - 无协议标准依赖
- 缺点：
  - 无法与 ChatGPT、Claude、Cursor 等 AI 助手原生集成，用户需要在 AI 客户端外手动执行并拷贝输出，严重损害使用流畅度
  - 不支持实时权限感知，Token 撤销与 ACL 变化无法在调用前实时生效
  - 多用户场景下每人需单独安装与配置 CLI，运维负担高
  - CLI 本质上也需要调用服务端 HTTP，相当于在 HTTP 层之上叠一层冗余包装

### 方案 F：remote MCP 服务（本专题主路线）

- 描述：在 Docmost 后端内嵌 remote MCP server，暴露 `/mcp` 入口，用户只需配置 URL + Bearer Token 即可在 AI 客户端中接入
- 优点：
  - AI 助手原生集成：Claude、Cursor 已原生支持 MCP，ChatGPT 支持 MCP 工具调用
  - 用户仅需配置 URL + Token，无需安装任何本地工具
  - 服务端实时校验 Token、ACL、限流，不依赖客户端行为
  - MCP 原生支持多模态 content block，为图片返回提供标准路径（详见图片专项）
  - 是 AI 工具集成的行业方向，生态成熟度持续提升
- 缺点：
  - 协议实现相对复杂，但已有成熟 SDK 可用

## 选型结论

**选择方案 F（remote MCP）作为唯一主路线，不开发 CLI 工具作为面向用户的正式接入协议。**

CLI 作为内部调试工具的可能性不排除，但不在正式范围内交付。

## 专项主题：图片内容接入策略

**决策日期**：2026-04-26

## 图片来源分类与处理策略

Docmost 页面中的图片分为以下四类，复杂度与处理策略各不相同：

| 类型 | 技术路径 | 阶段 |
| --- | --- | --- |
| 页面附件图（用户上传的 PNG/JPG/GIF 等） | `fetch` 返回附件 URL 列表；Phase 2 升级为 base64 content block | Phase 1 → Phase 2 |
| Mermaid / 代码图表 | 返回原始 Mermaid 或 PlantUML 源码，AI 可直接理解语义 | Phase 1（随正文 Markdown 自然携带） |
| 富文本渲染内容（表格、卡片等） | Markdown 序列化已覆盖大部分场景 | Phase 1 |
| 页面整页截图（headless browser 渲染） | **不做**，成本高、稳定性差、AI 实际需要的是结构化内容而非像素图 | 非目标 |

## 分阶段实现方案

### Phase 1（Wave 1.1）：附件图片 URL 随 fetch 返回

- `fetch` 响应新增 `attachments[]` 字段，包含页面内所有图片附件的 URL、MIME 类型、尺寸信息
- AI 客户端可按需自行请求图片 URL（适合支持图片理解的模型）
- 实现成本低，不引入 base64 序列化开销

### Phase 2（Future Stage A）：MCP content block 内联图片

- `fetch` 升级为返回 MCP 标准 `image` content block（base64 编码）
- 支持视觉型 AI 客户端（如 Claude）在单次工具调用内直接理解图片内容，无需二次请求
- 需要评估图片大小限制，超大图片保留 URL fallback 路径

## 非目标确认

- 不做页面整页截图（headless browser）
- 不做图片内容的服务端 OCR 或描述生成（由 AI 客户端自行处理）
- 不做视频、音频附件的内容理解
