## 背景与目标

### 背景问题

1. 升级到 `v0.70.1` 后，设置页出现多个企业版灰菜单，业务方明确希望具备类似能力。
2. 当前仓库同时受 AGPL 与企业版许可双重约束，不能把“直接拷企业版代码”当作默认实现方式。
3. 如果不建立明确的合规替代路线，后续会在法务、升级兼容、代码归属与运维上同时失控。

### 目标指标

1. 在不直接复制企业版代码的前提下，于 3 个阶段内交付 4 个核心替代能力：
   - 个人 API Token
   - 工作区 API Token 管理
   - 安全策略与 SSO
   - 审计日志
2. 首期上线后，Workspace Owner 与 Admin 可以在设置页完成上述能力的核心配置，无需额外控制台。
3. 所有新增模块必须具备可追溯的“代码来源说明”，在 Code Review 中可证明未复制 `ee` 目录源码。
4. 当前路线已确认在 AGPL 主仓内实现，因此必须同步交付源码获取入口、版本归档与第三方许可证清单。

## 现状审计（As-Is）

- 现有页面/交互盘点：设置侧栏存在灰菜单；页面定义主要位于 `apps/client/src/ee/**`
- 现有接口盘点：API Key、License、Audit、SSO 的完整后端接口并未在当前自托管开源路径中完整暴露
- 现有数据表盘点：已有基础工作区、用户、空间表；新增 `audit` / `page_access` 等迁移存在，但不宜默认直接复用
- 现有权限与埋点盘点：Workspace 角色、JWT、Workspace 上下文可复用；审计在无 EE 时默认退化为 `No-op`

## 改造策略确认闸门

## 能力复用与重复建设审查

- existing_scan：已审计设置页、`ee` 前端、动态加载后端、迁移与 License 校验路径
- build_vs_reuse：current-agpl-repo-self-build
- non_reuse_reason（若 new_build 必填）：企业版许可边界明确，不允许沿用企业版实现文本；当前路线下 AGPL 义务已确认接受并需持续履约
- consolidation_plan：

## 系统用户与角色

| 角色 | 目标 | 关键任务 | 权限边界 |
| --- | --- | --- | --- |
| Workspace Owner | 定义工作区安全策略与审计规则 | 开启/关闭策略、查看审计、设置保留期 | 拥有全部工作区级配置权限 |
| Workspace Admin | 管理成员与集成接入 | 创建/回收 API Token、配置 IdP、限制成员创建 Token | 不可越权操作 Owner 级保留策略 |
| 成员 / 开发者 | 使用个人 API Token 完成集成 | 创建、查看、撤销自己的 Token | 不可查看他人 Token |
| 安全/合规负责人 | 追溯关键管理操作 | 查询审计日志、按事件筛选、导出审计报告 | 默认只读或 Owner 授权只读 |

## 典型用户故事

1. 作为 Workspace Admin，我希望为自己和服务账号创建受限的 API Token，以便安全接入机器人和外部系统。
2. 作为 Workspace Owner，我希望配置公开分享、SSO、MFA 等安全策略，以便降低数据外泄和弱认证风险。
3. 作为安全负责人，我希望看到成员、Token、空间策略变化的审计日志，以便进行追责与合规留档。
4. 作为成员开发者，我希望自助管理自己的 Token，并清楚看到权限范围和最后使用时间，以便减少凭证滥用。

## 范围定义

### P0 决策前置

- 明确企业版代码禁止复制边界
- 固化 AGPL 履约方案：源码仓库、发布归档、获取入口、版本映射
- 明确首期 capability 开关与灰度工作区名单

### P1 首期范围

- 个人 API Token 管理
- 工作区 API Token 管理
- API Token 限制为管理员创建/管理的开关
- 审计日志写入、查询、保留期设置
- 设置页源码入口
- `/api/version.sourceUrl`

### P2 第二阶段

- 安全策略页
- 公开分享禁用
- 域名限制
- 强制 MFA
- 基础 OIDC SSO

### P3 第三阶段

- SAML
- LDAP
- 更完整的策略审计
- 更细粒度的 Token Scope

## 非目标

1. 不复刻 `Billing`、`License & Edition`、云租户计费与试用流程。
2. 不首期实现页面级权限、评论增强、附件全文检索等更高复杂度能力。
3. 不提供任何“如何避开开源协议公开义务”的操作方案。

## 产品原则

1. 功能可替代，但代码实现必须可溯源。
2. 用户体验可以接近原菜单，不要求 UI 一模一样。
3. 首期优先交付“安全收益高、法务风险可控、实现闭环清晰”的能力。
4. 所有高风险写操作都必须带审计。
5. 每个正式部署版本都必须可追溯到对应源码快照。

## 页面与入口策略

### 推荐入口

- `/settings/account/api-keys`
- `/settings/api-keys`
- `/settings/security`
- `/settings/audit`

### 推荐策略

- 保留现有路径，减少认知成本
- 但路由指向新建的自研页面目录，不再依赖 `@/ee/*`
- 侧栏禁用态改为根据 `workspace.capabilities` 或新配置项控制，而不是 `hasLicenseKey`
- 设置页源码入口文案默认使用 `Source Code`

## 改造影响矩阵与灰度切换

| 链路 | 现状 | 目标 | 风险 | 灰度方式 |
| --- | --- | --- | --- | --- |
| 设置页菜单 | 灰态不可点 | 按 capability 可用 | 中 | 测试环境先开 |
| Token 创建链路 | 不可用 | 自研 CRUD + scope | 高 | 先 Admin，后成员 |
| 审计写入链路 | `No-op` | 真实写表 | 高 | 双写校验 1 周 |
| 源码获取入口 | 无稳定入口 | 设置页 + `sourceUrl` | 中 | 先测试环境验证 |
| 安全策略链路 | 不可用 | 自研工作区策略 | 高 | 功能开关按工作区 |
| SSO 登录 | 不可用 | OIDC 二期接入 | 高 | 仅测试工作区灰度 |

- 灰度策略（维度、节奏、监控）：
  - 维度：环境、工作区、角色
  - 节奏：测试环境 -> 小范围 Owner/Admin -> 全员
  - 监控：登录成功率、Token 创建成功率、审计写入量、错误率
- 回滚策略（触发条件、步骤、时长）：
  - 触发条件：登录中断、审计写入异常、Token 误授权
  - 步骤：关闭 capability 开关 -> 路由回退为灰态 -> 停用模块入口 -> 保留只读数据
  - 时长：配置回滚 5 分钟内，代码回滚 30 分钟内

## 验收标准

### 功能验收

- Admin 可创建、查看、撤销工作区级 Token
- 成员可在策略允许时创建个人 Token
- Owner 可查看审计日志并设置保留期
- 设置页中存在可访问的源码获取入口，并能定位到当前运行版本
- `/api/version` 响应中包含 `sourceUrl`

### 接口验收

- 所有新接口需要统一鉴权、错误码、分页与审计埋点
- Token 明文只在创建时返回一次
- 审计日志列表支持 cursor 分页与事件筛选

### 回归验收

- 不影响现有登录、页面编辑、分享、备份
- 升级上游后菜单与 capability 逻辑仍可合并
- 测试与生产切换不破坏现有 `book` / `book-test` 路由
- 源码获取入口、版本号与部署提交号保持一致
- `Wave 1` 不引入登录链路变更
