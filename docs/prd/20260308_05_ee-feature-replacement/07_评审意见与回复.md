本文档用于记录评审问题、回复与采纳状态。阅读时当前系统实现可能已发生变化，请以实际代码与产品行为为准，谨慎参考。

## 评审问题与回复

### Q1：能不能直接复用灰菜单对应的企业版代码？

- 评审意见：这样最快。
- 回复：不采纳。`apps/client/src/ee/**` 已明确受企业版许可约束，直接复制风险不可接受。
- 采纳状态：拒绝
- 风险说明：权属不清、合规不可审计、后续升级不可维护

### Q2：既然主仓是 AGPL，是否可以直接在当前仓实现？

- 评审意见：可在当前仓开发，节省成本。
- 回复：采纳。当前已确认接受 AGPL 网络部署义务，因此后续灰菜单替代能力统一在当前主仓自研实现。
- 采纳状态：采纳
- 风险说明：前提是同步落实源码获取入口、版本归档和许可证保留

### Q3：如果不复制代码，能否照着相同的功能做？

- 评审意见：希望用户体验尽量一致。
- 回复：采纳。允许在功能与交互层面对标，但实现必须 clean-room。
- 采纳状态：采纳
- 风险说明：需避免行级复制、结构性照搬和名称耦合

### Q4：能否继续使用原来的设置路径？

- 评审意见：保留 `/settings/security` 等路径更省心。
- 回复：采纳。可保留用户路径，但路由组件与服务实现必须替换为自研模块。
- 采纳状态：采纳
- 风险说明：需要处理与上游未来路由变更的冲突

### Q5：审计表和 API Key 表能否复用上游已新增的表？

- 评审意见：复用能减少开发量。
- 回复：暂不采纳。首期默认使用 `sc_*` 新表，避免与企业能力含义耦合。
- 采纳状态：暂不采纳
- 风险说明：若未来要与官方能力共存，表语义冲突风险高

### Q6：是否必须购买商业授权？

- 评审意见：购买授权可能最稳。
- 回复：不作为当前路线。当前已明确采用 AGPL 主仓自研方案；商业授权仅保留为未来战略备选。
- 采纳状态：备选
- 风险说明：商业依赖与定制边界受限

### Q7：接受 AGPL 后，是否只需要保留内部源码备份？

- 评审意见：只要内部能找回代码即可。
- 回复：不采纳。需要让远程使用当前服务的用户有机会获得对应源码，不能仅保留内部备份。
- 采纳状态：拒绝
- 风险说明：如果没有稳定的源码获取入口，实际部署仍可能不满足 AGPL 履约要求

### Q8：设置页源码入口文案采用什么更合适？

- 评审意见：可选 `Open Source`、`Source Code` 或中文版本。
- 回复：采纳 `Source Code`。原因是最短、最直接，且与 `/api/version.sourceUrl` 命名一致。
- 采纳状态：采纳
- 风险说明：若后续品牌或国际化策略变化，可仅调整文案，不影响接口和履约方案

### Q9：是否保留与原菜单一致的中文名称？

- 评审意见：尽量减少用户学习成本。
- 回复：采纳。除新增 `Source Code` 入口外，现有菜单中文名称与信息架构保持不变。
- 采纳状态：采纳
- 风险说明：若后续官方菜单结构变化，需要在升级时重新做映射校验

## 风险复盘结论

1. 最大风险不是功能做不出来，而是做出来后权属不清。
2. 次高风险是把企业版命名、表结构、服务路径搬进当前仓，导致后续升级反复冲突。
3. 因此本专题优先把风险显式化，而不是只追求功能完成度。
