# 02 技术方案：架构与接口

**成文日期**：2026-03-08 23:07:46 UTC+8
**最后修订**：2026-03-08 23:47:55 UTC+8

本文档用于定义技术架构、接口契约与兼容策略。阅读时当前系统实现可能已发生变化，请以实际代码与产品行为为准，谨慎参考。

---

## 技术目标

1. 提供与企业版灰菜单对应的可用能力。
2. 不直接复制 `ee` 目录源码或其等价翻译版本。
3. 保留升级上游时的可维护性，避免再次出现大面积 merge 冲突。
4. 所有 API 契约与权限边界清晰可测。

## 技术原则

### 1. 源代码来源分级

- Green：当前 AGPL 仓中的通用壳层、路由容器、通用组件、用户与工作区上下文、第三方标准协议库
- Yellow：行为借鉴与黑盒参考，只允许抽象产品需求，不允许搬运实现文本
- Red：`apps/client/src/ee/**`、当前或未来 `apps/server/src/ee/**`、任何动态加载企业模块源码

### 2. 命名隔离

- 不新增 `ee` 前缀目录
- 自研能力建议放入 `apps/client/src/features/compliance-admin/**`
- 服务端建议放入：
  - `apps/server/src/core/integration-token/**`
  - `apps/server/src/core/security-policy/**`
  - `apps/server/src/core/idp/**`
  - `apps/server/src/core/audit-log/**`

### 3. 路由可兼容，内部实现不耦合

- 用户可继续访问原设置路径
- 页面组件与服务接口替换为自研实现
- 不依赖原企业版 lazy import

## 架构选项对比

### 方案 A：当前仓内直接扩展

- 做法：在现有 Docmost 仓内新增模块与接口，复用 AGPL 核心壳层
- 优点：接入成本低，UI 与上下文整合最好，最利于复用现有权限与工作区上下文
- 风险：必须持续履行 AGPL 网络部署义务，且每次发布都要维护对应源码获取入口
- 适用：公司明确接受 AGPL 义务，并愿意按协议提供修改后版本源码

### 方案 B：独立 sidecar clean-room 服务

- 做法：在独立仓实现 Token、SSO、Audit 等能力，通过稳定 API 与当前前端集成
- 优点：最有利于与现有 AGPL/EE 边界隔离
- 风险：工程复杂度更高，登录态、鉴权与部署链路更长
- 适用：公司不希望新能力直接落在当前 AGPL 仓内

### 方案 C：购买商业授权

- 做法：采购官方或合法商业授权，直接启用企业版能力
- 优点：交付最快，法律边界最清晰
- 风险：成本、定制自由度、供应商依赖
- 适用：时间优先且预算可接受

### 推荐

- 已选定：`方案 A`
- 备选：`方案 B` 仅在未来合规策略调整或需要进一步隔离时再评估
- 明确拒绝：任何“直接复制企业版实现”的变体

## 推荐架构

### 前端

- 新增目录：`apps/client/src/features/compliance-admin/`
- 新页面：
  - `pages/user-api-tokens.tsx`
  - `pages/workspace-api-tokens.tsx`
  - `pages/security-policies.tsx`
  - `pages/audit-events.tsx`
- 路由映射：
  - `/settings/account/api-keys` -> `user-api-tokens`
  - `/settings/api-keys` -> `workspace-api-tokens`
  - `/settings/security` -> `security-policies`
  - `/settings/audit` -> `audit-events`

### 后端

- 新模块：
  - `IntegrationTokenModule`
  - `SecurityPolicyModule`
  - `IdentityProviderModule`
  - `AuditLogModule`
- 新能力统一读取 `workspaceId` 与当前用户角色
- 关键写操作统一调用自研 `AuditLogService`

## AGPL 履约设计

### 版本与源码映射

- 每次测试、生产部署都记录：
  - `git commit sha`
  - 应用版本号
  - 部署时间
  - 对应源码归档位置
- 推荐在仓库内维护 `docs/open-source/releases/{version}.md` 或等价清单

### 源码获取入口

- 需要在产品内提供稳定入口，推荐位置：
  - 设置页底部 `Source Code`
  - `/api/version` 响应中追加 `sourceUrl`
- 入口需指向当前运行版本的源码，而不是泛指主分支仓库首页
- 当前已确认采用：`设置页底部入口 + /api/version.sourceUrl`

### 归档要求

- 保留当前运行版本的完整源码快照
- 保留构建与部署所需脚本
- 保留第三方依赖许可证清单
- 保留本地定制功能的说明文档与版本差异摘要

### 能力开关

- 在 `workspace` 或新 `workspace_capabilities` 中暴露 capability
- 推荐 capability：
  - `integrationTokens`
  - `workspaceTokenManagement`
  - `securityPolicies`
  - `identityProviders`
  - `auditLogs`

## API 契约

### 1. 个人 Token

- `POST /api/integration-keys/list`
- `POST /api/integration-keys/create`
- `POST /api/integration-keys/update`
- `POST /api/integration-keys/revoke`

字段约束：

- `name`: 必填，长度 <= 64
- `scopes`: 数组，首期限定为预置 scope
- `expiresAt`: 可选
- `lastUsedAt`: 只读

### 2. 工作区 Token 管理

- `POST /api/admin/integration-keys/list`
- `POST /api/admin/integration-keys/create`
- `POST /api/admin/integration-keys/update`
- `POST /api/admin/integration-keys/revoke`
- `POST /api/admin/integration-keys/policy`

权限：

- 仅 `Admin` 以上
- `policy` 更新仅 `Owner` 或特定管理员

### 3. 安全策略

- `POST /api/security-policies/get`
- `POST /api/security-policies/update`

首期字段：

- `disablePublicSharing`
- `restrictApiTokenCreationToAdmins`
- `enforceMfa`
- `allowedEmailDomains`
- `defaultTokenTtlDays`

### 4. 身份提供商

- `POST /api/auth-providers/list`
- `POST /api/auth-providers/create`
- `POST /api/auth-providers/update`
- `POST /api/auth-providers/delete`
- `POST /api/auth-providers/test`

首期 provider：
- 二期：`oidc`
- 三期：`saml`
- Future：`ldap`

### 5. 审计日志

- `POST /api/audit-events/list`
- `POST /api/audit-events/retention`
- `POST /api/audit-events/retention/update`

查询参数：

- `cursor`
- `limit`
- `event`
- `actorId`
- `resourceType`
- `dateFrom`
- `dateTo`

## 契约设计规则

1. 不沿用企业版服务名和目录名。
2. 不要求接口路径与企业版完全一致，但用户可见路由尽量一致。
3. 所有写接口必须：
   - 鉴权
   - 权限校验
   - 审计记录
   - 幂等或去重说明
4. 所有版本查询接口应返回可用于定位对应源码的版本信息
5. `Wave 1` 不改动登录入口、认证回调与会话签发链路

## 与当前主系统的集成点

### 用户与工作区上下文

- 复用现有 JWT、`workspaceId`、`AuthUser`、`AuthWorkspace`
- 扩展 `users/me` 或 `workspace/info` 返回 capability

### 公共 UI

- 复用设置页布局、表格、弹窗、分页、表单组件
- 不复用 `@/ee/*` 页面实现

### 审计事件接入

- 页面、空间、成员、Token、策略等关键写操作通过统一 `AuditLogService` 记录
- 不依赖当前默认 `NoopAuditService`

## 兼容策略

1. 自研能力默认以 capability 控制显示，不依赖 `hasLicenseKey`
2. 首期可保留灰菜单逻辑，在 capability 开启后逐项切换
3. 若上游未来开放同类 OSS 能力，可评估是否收敛或迁回原生实现
4. `License & Edition` 页如继续保留，需补充自研能力与源码入口说明，避免误导为官方企业授权能力
5. `sourceUrl` 优先从后端版本接口下发，前端不硬编码源码地址

## 不采纳方案

- 直接复制 `apps/client/src/ee/**`
- 从企业版目录改变量名后继续使用
- 直接把企业版迁移文件、表名、服务名整套搬过来作为自研实现
