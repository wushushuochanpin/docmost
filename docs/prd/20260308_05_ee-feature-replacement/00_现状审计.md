## 现状结论

当前“灰色菜单”不是纯占位。它们对应真实产品能力与前端页面，但默认受企业版授权控制；在当前自托管、无 LicenseKey 的前提下，前端会展示为禁用态，后端部分能力会退化为 `No-op` 或动态加载失败。

## 当前证据汇总

### 1. 许可边界

- 仓库根目录 `LICENSE` 为 `GNU AGPL v3`。
- `apps/client/src/ee/LICENSE` 明确写明：`Files in this directory are subject to the SuperChat Enterprise Edition license.`
- 当前仓库既包含 AGPL 核心代码，也包含企业版前端页面与若干动态加载入口，属于典型 `open-core` 结构。

### 2. 灰菜单并非占位

设置侧栏中以下项被显式标记为 `isEnterprise`，且 `showDisabledInNonEE=true`：

- `API keys`
- `Security & SSO`
- `API management`
- `Audit log`

这些项的前端页面都存在于 `apps/client/src/ee/` 下，说明产品层面是真功能，而不是未来占位。

### 3. 后端并非全部缺失，但能力不完整

- `Audit` 相关数据库迁移与事件枚举已存在。
- 当前核心模块默认注入 `NoopAuditService`，意味着在没有企业实现时，审计写入会被吞掉。
- API Key 校验逻辑会动态 `require('../../../ee/api-key/api-key.service')`；企业模块不存在时直接拒绝。
- License 校验服务会动态 `require('../../ee/licence/license.service')`；未加载到时返回 `false`。

### 4. 测试与生产当前状态

- 生产与测试都已升级到 `v0.70.1`。
- 测试环境所谓“热加载”仅对前端 `vite dev` 成立，后端仍是 `server:build + start:prod` 形式。
- 升级过程中已经出现过企业特性相关的两类兼容问题：
  - 审计依赖注入缺失
  - 迁移顺序冲突

## 问题定义

### 业务问题

业务方希望获得以下类似能力：

1. 用户 API Token
2. 管理员 API Token 管理
3. 工作区安全与 SSO
4. 审计日志

### 合规问题

直接复用企业版代码会触碰两个边界：

1. `ee` 目录的企业版许可边界
2. AGPL 网络部署义务边界

### 工程问题

如果不先做“来源分级”和“实现边界”确认，后续很容易出现三类风险：

1. 代码层面混用 AGPL 与企业版实现，导致权属不清。
2. 为了贴近原功能而沿用同名路径、同名表、同名服务，增加后续合并与审计风险。
3. 在当前主仓库内直接堆叠新逻辑，未来升级上游再次发生大面积冲突。

## 已确认决策

1. 业务接受 AGPL 网络部署义务，后续灰菜单能力在当前主仓内自研实现。
2. 企业版 `ee` 目录及其实现文本仍然禁止直接复制、改名改写或结构性照搬。
3. 后续所有上线版本需要具备“对应源码获取入口”，而不是仅在有人询问时临时提供。

## 系统用户与角色

| 角色 | 当前任务 | 痛点 | 高风险操作 |
| --- | --- | --- | --- |
| Workspace Owner | 负责安全与审计策略 | 看得到灰菜单但无法用 | 开启 SSO、调整审计保留期 |
| Workspace Admin | 负责成员接入、集成与 API 访问 | 无法统一发放或回收 Token | 创建全局 Token、限制成员权限 |

## 代码来源分级（合规审计）

### Green：允许复用，但需遵守 AGPL 或原始许可

- `apps/client/src/components/**`
- `apps/client/src/features/**` 中非 `ee` 页面骨架
- `apps/server/src/core/**` 中通用 Repo、Guard、中间件、审计事件枚举
- 第三方标准协议库与其许可兼容代码

### Yellow：默认不直接复制，只能借鉴行为与数据流

- 与企业版功能强相关、但位于非 `ee` 目录的表结构或迁移命名
- 升级中新增的 `page-permissions`、`audit` 等功能域设计
- 产品行为、按钮布局、字段集合、接口语义

处理原则：允许阅读与总结行为，不允许直接拿实现文本、结构或命名照搬。

### Red：不得直接复制或变相翻译

- `apps/client/src/ee/**`
- 当前或未来 `apps/server/src/ee/**`
- 任何动态加载企业模块后拿到的实现源码
- 企业许可目录中的样式、组件、接口封装、业务逻辑

## Build vs Reuse 结论

- existing_scan：已完成；当前仓库存在可复用 OSS 壳层，但企业能力主体不可直接抄用。
- build_vs_reuse：`current-agpl-repo-self-build`
- 复用范围：导航框架、权限基座、Workspace 上下文、通用列表与表单组件、标准协议三方库
- 新建范围：API Token、审计日志、安全策略、SSO Provider 管理、相关表与接口
- non_reuse_reason：企业版许可边界清晰；直接复用将引入权属与发布义务不确定性

| 影响对象 | 现状行为 | 改造后行为 | 风险等级 | 回归范围 |
| --- | --- | --- | --- | --- |

| 用户信息接口 | 仅返回 `hasLicenseKey` 等 | 新增 capability 字段 | 中 | 前后端契约 |

## 结论

首期不能以“复制企业版代码”作为方案。推荐形成新的“合规替代能力”产品线：

1. 功能表现接近企业版
2. 代码实现独立、可审计、可回溯
3. 数据表与接口命名避免与企业版强绑定
4. 接受 AGPL 后同步落地源码获取入口与版本归档，不做“只改代码不履约”的隐性承担
