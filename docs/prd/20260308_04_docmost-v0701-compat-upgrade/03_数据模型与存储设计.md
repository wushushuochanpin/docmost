# 03 数据模型与存储设计：迁移整合与存储兼容

**成文日期**：2026-03-08 20:57:06 UTC+8
**最后修订**：2026-03-08 20:58:36 UTC+8

本文档用于定义核心实体、字段与存储策略。阅读时当前系统实现可能已发生变化，请以实际代码与产品行为为准，谨慎参考。

---

## 数据设计原则

1. 不重命名已在线上执行过的本地 migration 文件。
2. 本地已存在的 schema 语义优先，新增上游能力走“加法迁移”。
3. 所有会影响权限、分享、备份和多租户隔离的表/列变更，必须先在 staging 演练。
4. `db.d.ts` 与实体类型生成结果必须以整合后的 migration 为准重新生成。

## 迁移冲突处理策略

### 1. 同主题但文件名不同的迁移

上游与本地在以下主题上存在“内容相近但文件名不同”的情况：

1. `add-settings-to-spaces`
2. `notifications`
3. `watchers`
4. `backfill-watchers`
5. `add-contributor_ids-to-page-history`

处理策略：

1. 保留本地已存在文件名，不将其替换为上游旧时间戳版本。
2. 以 migration 表中的已执行记录为准，避免线上出现重复执行或缺失执行。
3. 若上游同主题迁移内容有额外差异，则新增兼容 migration，而不是直接覆盖原文件。

### 2. 纯新增上游迁移

| 迁移 | 处理 |
| --- | --- |
| `page-permissions` | 作为新增迁移并入，先验证与本地 RLS/folder-first 的兼容性 |
| `audit` | 作为新增迁移并入，注意不影响当前分享/工作区操作写链路 |

### 3. 本地独有迁移

下列迁移在本地是产品关键域，升级时必须保留：

1. `folder-first-shared-db-rollout`
2. `full-tenant-rls-rollout`
3. `backup-tables`
4. `performance-hardening-indexes`
5. `tenant-consistency-fks`
6. `share-protected-access`
7. `backup-artifact-delete-columns`

## 目标数据模型

### 保留域

| 域 | 数据语义 | 升级要求 |
| --- | --- | --- |
| 页面/树/RLS | 本地多租户与 folder-first | 不可逆改动前必须有 staging 验证 |
| 分享 | password expiry、static renderer、微信分享元数据 | 字段与查询语义保持兼容 |
| 备份 | job、artifact、restore 相关数据 | 保留全部表结构和后续扩展位 |

### 新增域

| 域 | 上游新增内容 | 兼容要求 |
| --- | --- | --- |
| notifications | 通知表、watchers、回填逻辑 | 不影响现有评论/提及查询 |
| page permissions | 页面级授权相关表 | 与本地树和 RLS 协同 |
| audit | 审计事件存储 | 与本地安全/运维审计口径不冲突 |

## 存储与运行时兼容

| 项 | 当前本地模型 | 升级后的处理 |
| --- | --- | --- |
| Postgres | 本地自建，含历史迁移 | 继续作为唯一权威库，先演练再升级 |
| Redis | 本地已接入 | 保持不变，兼容通知/ws 能力 |
| Storage | 本地 `data/storage` + S3/COS 兼容配置 | 保留备份与分享现有读写方式 |
| Event Store | 当前未启用 ClickHouse | 变量可并入，但默认不启用 |

## 迁移步骤

1. 备份 staging 和 production 数据库快照。
2. 在升级分支整合 migration 列表与类型定义。
3. 先在 staging 全量执行 migration。
4. 校验 migration 表记录、关键表结构、索引与约束。
5. 运行回归用例后才允许生产执行。

## 回滚策略

1. 优先通过应用版本回滚解决代码问题。
2. 数据库层只接受“加法迁移优先”的方案，尽量避免必须立即逆向 DDL 的场景。
3. 若 `page-permissions` 或 `audit` 引发逻辑问题，优先关闭入口和写入逻辑，而不是直接删表。

## 验收标准

1. 升级前后关键本地表结构保持兼容。
2. 上游新增表与索引在 staging 成功创建。
3. `db.d.ts`、`entity.types.ts` 与真实 schema 一致。
4. migration 执行顺序与历史执行记录可解释、可追溯。
