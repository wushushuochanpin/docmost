## 背景

1. 当前仓库版本号仍为 `0.25.3`，但本地主线已经在官方共同基线 `c172d3bd` 之后沉淀了 `47` 个本地提交；与 `upstream/main` 相比，处于 `47 / 53` 的双向分叉状态。
2. 本地主线已扩展目录树、多租户/RLS、深色主题、编辑器工具栏、Mermaid 预览、分享 SSR/静态渲染/微信分享、备份与恢复方案等能力，不能被官方升级覆盖。
3. 上游 `v0.25.3 -> v0.70.1` 又引入页面内容 API、通知、编辑器 UI、页面级权限、状态节点、评论增强、用户停用、搜索优化等一组产品能力，其中多项命中本地已改代码区域。
4. 用户目标不是“追版本号”，而是“把上游新能力吃进来，同时保住本地业务化改造，并把以后继续跟上游的成本降下来”。

## 关键决策

1. 升级策略不采用“直接覆盖官方代码”，而采用“从当前 `main` 开升级分支，合并 `v0.70.1`，按模块手工保留本地能力”的兼容过渡方案。
2. 发布基线以 `v0.70.1` tag 为准，不直接追 `upstream/main`；未发布主干提交留到后续小版本再评估。
3. 当前本地部署/环境配置、分享链路、备份链路、租户/RLS 改造和 UI 定制能力全部列为“保护域”，升级时禁止被官方默认实现替换。
4. 对 `feat(ee)` 标记的上游能力，区分“代码并入”和“业务开放”两层验收；若 enterprise gating 未打通，则先完成代码并入与隐藏开关接线，不阻塞本次基线升级。
5. 数据库迁移采用“保留已执行本地 migration 文件名 + 追加缺失上游迁移 + 不重命名线上已执行记录”的原则。
6. 整体实施采用分波次推进：基线合并、迁移整合、核心回归、灰度环境、生产切换。

## 非目标

1. 本次不把系统整体迁移到 `upstream/main` 最新未发布提交。
2. 本次不接受用官方 `docker-compose.yml` 或 `docmost/docmost:latest` 镜像替换当前本地构建与部署方式。
3. 本次不删除本地分享、备份、主题、RLS、目录树等任何既有能力。
4. 本次不把所有 enterprise 能力立刻在生产开放给终端用户；若 license/build gating 未完成，可阶段性隐藏入口。
5. 本次不顺手做新的产品需求扩张，升级范围只围绕“并入上游能力 + 保持本地兼容”。
