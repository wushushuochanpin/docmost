# 09 未来实现草案

**成文日期**：2026-03-08 20:57:06 UTC+8
**最后修订**：2026-03-08 20:58:36 UTC+8

本文档用于描述升级完成后的未来阶段、持续演进方向与风险。阅读时当前系统实现可能已发生变化，请以实际代码与产品行为为准，谨慎参考。

---

## 未来阶段划分

| 阶段 | 目标 | 产物 |
| --- | --- | --- |
| Phase 1 | 完成 `v0.70.1` 兼容升级 | 可运行主线、迁移基线、回归清单 |
| Phase 2 | 拆出本地长期保护域，降低下一次升级成本 | 模块边界、feature gate、保护域清单 |
| Phase 3 | 建立持续同步上游节奏 | 月度同步机制、季度大版本评估 |

## 未来优化方向

### 1. 把本地定制从“散落改动”收敛成明确模块

重点对象：

1. 分享域
2. 备份域
3. 主题与品牌壳
4. folder-first / RLS 扩展层

目标：

1. 以后升级时尽量减少直接改官方核心文件。
2. 通过 wrapper、service extension、feature gate 降低重叠文件数。

### 2. 建立升级基线标签与差异清单

建议每次合并官方版本后固化：

1. 一个 `after-upstream-vX.Y.Z` tag
2. 一份“保护域清单”
3. 一份“本地新增 capability 清单”

### 3. 分层处理 enterprise 能力

对 `audit / MCP / AI / page permissions / API key restriction`：

1. 代码层跟上上游。
2. 产品层按业务需要决定开放策略。
3. license/build gating 单独维护，不与主功能逻辑耦合。

## 长期风险

1. 如果升级后仍继续把业务能力直接改在官方核心文件里，下一次升级风险不会下降。
2. 如果不建立固定同步节奏，未来阶段又会回到“大跨度一次性升级”的高风险模式。
3. 如果 EE gating 不清晰，未来阶段每次引入企业特性都会出现 UI 与后端模块错位风险。

## 建议制度化动作

1. 每月一次上游差异审计。
2. 每次业务定制开发前先判断是否落在保护域。
3. 对高重叠文件建立 Code Owner 或 reviewer 规则。

## 未来阶段验收

1. Phase 1 后，分叉面明显缩小且升级流程形成模板。
2. Phase 2 后，分享/备份/主题/RLS 至少具备一层模块边界。
3. Phase 3 后，下一次升级不再需要 large 级专题评估。
