## 问题与约束

1. 当前仓库不是“官方 `0.25.3` + 少量 patch”，而是业务化深度分叉版本。
2. `docker-compose.yml`、`Dockerfile`、`.env.example`、`apps/client/vite.config.ts` 均有本地部署/开发约束，不能被官方默认文件替换。
3. 本地 share、backup、RLS、folder-first 都属于核心业务链路，一旦被覆盖，会直接产生功能回退或数据隔离风险。
4. 上游 `feat(ee)` 代码虽然可并入，但真正对用户开放还依赖 `apps/server/src/ee` 动态加载与 license 判断；如果盲目开放，会出现入口可见但后端未授权的问题。
5. 数据库迁移不能以“重命名文件对齐上游”为手段解决冲突，因为线上 migration 记录已经绑定本地文件名。

## 已知风险

1. 编辑器与页面树冲突面最广，是本次升级最主要的人力消耗点。
2. 迁移文件若处理不当，会出现“代码可编译但数据库基线不一致”的隐性风险。
3. EE 功能若未明确 gating 策略，容易在 UI 和 API 两端产生不一致。
4. 若直接采用上游 compose/deploy 文件，会导致本地自定义运行方式丢失。
