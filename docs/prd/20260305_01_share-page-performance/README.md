## 需求确认结论

1. 现象：分享页在移动端（微信内置浏览器、H5）打开缓慢；用户感知为白屏长、正文晚、页面像“主站全量能力”被带进来了。
2. 根因：分享链路虽已完成第一轮减重，但正文仍依赖 TipTap 只读运行时；手机端仍要下载、解析、初始化编辑器相关能力。
3. 目标：让用户先尽快看到可读内容，再按需补齐目录、搜索、主题、重型内容渲染器。
4. 范围：仅改造分享域（`/share/*`）访问链路与首屏运行时；不改变主站非分享路由行为。

## 已确认业务取舍

1. 允许重内容先占位、后加载：Drawio、Excalidraw、Embed 等非正文核心内容可先显示轻量占位，再按需加载完整渲染器。
2. 搜索、TOC 不阻塞正文首屏：这些能力仍要保留，但不再要求“正文出现前就准备完毕”。
3. 分享页走独立化方向：目标架构为独立 share entry / share app，可分阶段迁移，不要求一次性推翻旧实现。
4. 二阶段允许服务端生成分享安全 HTML：正常分享正文路径默认不再挂载 TipTap 只读运行时，而是渲染静态 HTML，再按需挂载少数交互块。
5. 分享页不保留手动深浅色切换：一期固定 Reader 浅色主题，不加载 palette 同步、主题切换按钮与本地存储监听；后续若确有需要，仅允许纯 CSS `prefers-color-scheme` 方案。
6. `Mermaid` 一期允许按纯展示代码块输出：先保证源码可读和区域语义正确，不把 `mermaid runtime` 带回分享页 happy path；后续如要补图形化，优先服务端 SVG。
7. 长文档优化采用“先瘦首包，再按块渐进加载”：先消除 `page.content + rendered.html` 的重复传输，再按顶层 block / HTML 字节做续传；不按 viewport 像素高度切内容。

## 关键决策

1. 第一优先级不是继续堆零碎拆包，而是把“分享阅读”从“编辑器实例”切换为“静态阅读内容”。
2. 分享页独立化是已确认方向，但它只是第一阶段减重；真正的数量级优化来自“正文脱离 TipTap 只读运行时”。
3. 重型块渲染与辅助壳层采用渐进增强：正文优先，辅助能力稍后补齐。
4. 推荐方案是“服务端静态 HTML 渲染 + 客户端渐进挂载”，不是把整个站点改造成 SSR/SSG。
5. 分享页要遵守 Reader Contract：代码块、Callout、Details、表格、附件等优先使用纯展示渲染，而不是“禁编辑的编辑器组件”。
6. `Mermaid` 不在一期分享页里恢复客户端图形运行时；先以灰底代码块展示源码，再视收益评估服务端 SVG。
7. 后端接口合并仅作为补偿项候选，不是静态阅读方案的前置条件。
8. 长文档的下一阶段优化不是“只显示第一屏”，而是“首段先可读 + 后续 chunk 自动补齐”；真正先做的是首包瘦身，而不是 viewport 切片。

## 非目标

1. 不把整个 Docmost 主站改造成 SSR/SSG 工程；静态 HTML 输出仅针对 `/share/*` 正文阅读链路。
2. 不改变分享链接格式与 SEO 规则（除加载方式外）。
3. 一期不新增持久化缓存表；若后续需要 renderer cache，优先内存或 Redis，不先做数据库迁移。
4. 不把分享页重做成一套新的产品能力；本质仍是复用现有 share domain 的业务语义。
5. 不保留分享页手动主题切换、配色面板同步与相关运行时监听。
