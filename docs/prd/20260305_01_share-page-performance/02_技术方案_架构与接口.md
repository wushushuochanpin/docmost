# 02 技术方案：架构与接口

## As-Is 技术现状（当前真实基线）

1. **分享入口已独立化**：`main.tsx` 会按 `/share/*` 动态加载 `bootstrap-share.tsx`，分享路由不再进入主站 `App`。
2. **正文优先已做过一轮**：`SharedPage`、`ShareRedirect` 已有 skeleton，`ShareShell` 已将树、搜索、TOC 做延迟加载。
3. **只读扩展已减重**：`ReadonlyPageEditor` 已通过 `getReadonlyExtensions(content)` 按特征装配只读能力，重型块 viewer 已拆成 lazy node view。
4. **仍然有一个根因未拔掉**：正常分享正文仍通过 `EditorProvider + TipTap extensions + ProseMirror JSON` 渲染；浏览器仍要承担 editor runtime、schema 构建、文档解析与 node view 装配。
5. **长文档仍有首包冗余**：静态 HTML 命中后，接口仍会把 `page.content` 与 `rendered.html` 同时返回；长文档首包存在重复正文 payload。

## 关键结论

1. 继续做“前端运行时拆包”不是没有价值，但收益已进入递减区。
2. 如果目标是数量级改善，必须让正常分享正文路径摆脱 TipTap 只读运行时。
3. 推荐方案不是“客户端再造一个 HTML renderer”，而是“服务端静态 HTML 渲染 + 客户端渐进挂载”。
4. 这不是全站 SSR/SSG 改造，而是分享页正文 API 返回一份 share-safe HTML。
5. 分享页不应继续保留手动主题切换、palette 同步与相关存储监听；这些能力不构成阅读核心价值，却会扩大 share happy path 的运行时和故障面。
6. 长文档不应按 viewport 像素高度切片，而应按顶层 block 或 HTML 字节做稳定分段。

## 方案候选比较

| 方案 | 描述 | 优点 | 硬伤 | 结论 |
| --- | --- | --- | --- | --- |
| A. 继续前端拆包 | 继续缩减 `readonly-extensions`、viewer、Provider | 工程改动小，风险低 | 收益递减，正文仍需启动编辑器 | 只能做补偿项，不是目标架构 |
| B. 客户端静态 HTML 渲染 | 浏览器拿 JSON 后本地转 HTML | 渲染模型更接近静态阅读 | 仍要把解析器和渲染逻辑下发到浏览器，移动端 JS 成本仍高 | 不推荐作为主方案 |
| C. 服务端静态 HTML 渲染 | 服务端将 page JSON 转 share-safe HTML，前端直接渲染 HTML | 去掉正文路径的编辑器运行时，最符合移动端性能目标；后端已有 `jsonToHtml / generateHTML` 能力可复用 | 需要解决保真、清洗、缓存、灰度回退 | 推荐方案 |

## 推荐方案：服务端静态 HTML 渲染 + 客户端渐进挂载

### 方案定义

1. 分享接口在返回 `share + page` 的同时，返回一份经过服务端生成和清洗的 `rendered.html`。
2. 前端 `SharedPage` 正常 happy path 直接渲染 `rendered.html`，不再挂载 `ReadonlyPageEditor`。
3. 客户端仅保留一个很小的“share runtime + hydrator registry”，扫描 HTML 中标记的交互块占位节点，并在需要时再挂载对应 viewer。
4. TipTap 只读路径保留为迁移期 fallback，不再是默认路径。

### 为什么不优先选客户端静态渲染

1. 客户端静态渲染仍要下发 ProseMirror/Tiptap 解析能力，本质没有摆脱“浏览器承担编辑器解析成本”。
2. 用户要的是“读正文”，不是“浏览器本地做一次 JSON -> HTML 编译”。
3. 现有后端已经存在 `generateHTML`、`jsonToHtml`、导出 HTML 的代码链，服务端静态渲染具备更好的复用基础。

## 目标分层架构

### Layer 1：Share Runtime

- 只保留分享页必要 Provider、路由、样式与错误边界。
- 尽量避免让与分享正文无关的 Query、Modal、Notification、Analytics 初始化进入 happy path。
- 一期不保留手动主题切换、palette 同步、`localStorage` 监听和主题切换按钮；分享页使用固定 Reader 浅色主题。

### Layer 2：Static Content Renderer

- 服务端读取分享页 ProseMirror JSON。
- 基于 share-safe extension 子集生成 HTML。
- 对 HTML 做额外清洗、URL 重写、交互块占位注入。
- 前端直接把清洗后的 HTML 插入到受控容器。

### Layer 3：Sparse Hydrators

- 仅对 Drawio、Excalidraw、Embed、重型媒体、少数 viewer 进行按块挂载。
- TOC 从 DOM 标题锚点或服务端 `toc` 数据构建，不再依赖 editor state。
- 搜索、树继续作为 enhancement 层，与正文主渲染解耦。

## Reader Contract（分享页纯展示契约）

1. 分享页默认输出是“阅读内容”，不是“禁编辑的编辑器实例”。
2. 每一种块类型都必须先定义分享态展示契约，再决定是否需要交互 runtime。
3. 只要纯展示能满足核心阅读目标，就不能为了复用编辑器组件把 node view 或 schema 重新带回 happy path。

### 关键块类型契约

| 块类型 | 分享态 Contract | 是否允许交互 runtime | 说明 |
| --- | --- | --- | --- |
| codeBlock | 输出静态 HTML：`<section class=\"share-code-block\" data-language=\"...\">` + `pre/code` | 仅允许极小复制增强 | 不再挂 `readonly-code-block-view`、`lowlight` 或编辑器 toolbar |
| mermaid | 一期按 `share-code-block` 输出源码，显式标记语言为 `mermaid` | 否 | 一期不恢复客户端 `mermaid runtime`；若后续要图形化，优先服务端 SVG |
| callout | 输出静态提示块 | 否 | 只保留阅读语义和样式，不保留编辑态交互 |
| details | 输出原生 `details/summary` | 否 | 复用浏览器原生交互，减少 JS；若隐藏原生 marker，必须补回可见 chevron / 展开提示 |
| table | 输出静态 `table` + 外层滚动容器 | 否 | 避免表格 node view 与编辑态 schema 依赖 |
| mention | 输出普通可点击链接 | 否 | 不引入 suggestion、popover 与编辑态查询 |
| attachment | 输出静态下载卡片 | 否 | 保留文件名、大小、下载入口 |

## 服务端渲染流水线

### 1) 数据输入

- 输入源：现有 `share -> page.content` 的 ProseMirror JSON。
- 复用能力：
  - `apps/server/src/common/helpers/prosemirror/html/generateHTML.ts`
  - `apps/server/src/collaboration/collaboration.util.ts` 的 `jsonToHtml`
  - `apps/server/src/core/page/page.controller.ts` 与 `apps/server/src/integrations/export/export.service.ts` 已存在的 HTML 输出链

### 2) 生成策略

1. 使用分享安全扩展子集生成 HTML，而不是直接把编辑态完整扩展链原样复用到分享 API。
2. 在生成前做 share-safe 归一化：
   - 去除评论态、协作态、编辑命令态结构
   - 将 mention / subpages 等特殊节点转成分享可读的静态语义
3. 在生成后做 HTML 后处理：
   - 注入 heading anchors
   - 给交互型块输出 `data-share-block` 占位标记
   - 统一附件、图片、媒体 URL 为 share-safe 公共访问地址

### 3) 输出结构

推荐优先扩展现有 `POST /shares/page-info`，响应新增 `rendered` 字段：

```json
{
  "share": {},
  "page": {},
  "rendered": {
    "html": "<article>...</article>",
    "contentHash": "sha256:...",
    "generatedAt": "2026-03-06T19:12:55+08:00",
    "toc": [
      { "id": "intro", "text": "Intro", "level": 2 }
    ],
    "interactiveBlocks": [
      { "id": "node-1", "type": "drawio" },
      { "id": "node-2", "type": "embed" }
    ],
    "rendererVersion": "share-static-v1"
  }
}
```

说明：

1. 优先扩展 `page-info`，因为它已经是正文首屏唯一必要请求；不应为了新方案额外增加一次 RTT。
2. 若后续发现渲染计算耗时或缓存策略需要强隔离，再评估独立 `POST /shares/rendered-page`。

## 前端渲染策略

### 1) 正文主路径

1. `SharedPage` 收到 `rendered.html` 后，直接渲染到受控容器，例如 `SharedPageHtmlContent`。
2. 容器只接受服务端清洗后的 HTML，不接受客户端拼接的富文本 HTML。
3. happy path 默认不创建 `readOnlyEditorAtom`，也不挂 `ReadonlyPageEditor`。
4. happy path 默认不初始化 `share-color-scheme.ts` 的 palette 同步、主题按钮或本地存储监听；Reader 主题由静态样式控制。
5. 代码块使用纯展示 DOM 结构和 CSS，不复用 `readonly-code-block-view.tsx`。
6. `Mermaid` 一期与普通代码块共享纯展示容器，源码可读优先于图形化。

### 2) 交互块挂载

1. 前端扫描 `rendered.interactiveBlocks` 或 DOM 上的 `data-share-block` 标记。
2. 为每种交互块注册 hydrator：
   - `drawio`
   - `excalidraw`
   - `embed`
   - `video/youtube`（如需要重型播放器）
3. hydrator 触发条件：
   - 进入视口
   - 用户点击
   - 页面 idle 且设备条件允许
4. `codeBlock` 与 `mermaid` 不属于一期 hydrator 范围。

### 3) TOC / 搜索 / 锚点

1. TOC 优先基于 `rendered.toc` 或 DOM heading 生成。
2. 锚点跳转直接操作 DOM，不依赖 editor selection/scroll helper。
3. 分享内搜索可继续做 enhancement 层：
   - 轻量方案：直接搜索 DOM 文本
   - 增强方案：消费后端提供的文本索引或 headings 摘要
4. 移动端 TOC 若以 drawer 呈现，点击目录项后必须自动关闭 drawer；桌面侧栏 TOC 保持打开，便于连续跳读。

## 请求与契约策略

### 推荐的一期 API 形态

1. 正文首屏仍只保留一个请求：
   - `POST /shares/page-info`
2. `page-info` 在 feature flag 开启时附带 `rendered`：
   - `rendered.html`
   - `rendered.toc`
   - `rendered.interactiveBlocks`
3. 保持现有字段兼容：
   - `page.content` 可保留，供 legacy fallback 使用
   - `share / hasLicenseKey / permission` 等既有语义不变

### 长文档优化的正确顺序

1. **Phase A：先瘦首包**
   - 当 `rendered.html` 可用时，`page-info` 不再回传整份 `page.content`
   - `page` 仅保留分享首屏必需字段，如 `id / slugId / title`
   - legacy fallback 仅在 `rendered` 缺失或渲染开关关闭时才需要 `page.content`
2. **Phase B：再做块级渐进加载**
   - 对超长文档，首包不再一次性返回整份 `html`
   - 首包返回 `headHtml + nextCursor` 或等价结构
   - 客户端在 idle 或接近底部时按游标续传剩余 chunk
3. **明确不做**
   - 不按“手机第一屏像素高度”切内容
   - 不先下载整篇 HTML 再只显示第一屏

### 推荐的二期分段契约

当文档超过阈值时，`rendered` 建议扩展为：

```json
{
  "html": null,
  "headHtml": "<p>...</p>",
  "nextCursor": "seg:2",
  "deliveryMode": "segmented",
  "segmentCount": 6,
  "toc": [],
  "interactiveBlocks": []
}
```

新增续传接口：

```json
POST /shares/page-segment
{
  "shareId": "share_xxx",
  "pageId": "page_xxx",
  "accessToken": "jwt",
  "cursor": "seg:2"
}
```

响应：

```json
{
  "html": "<section>...</section>",
  "nextCursor": "seg:3",
  "interactiveBlocks": [],
  "segmentIndex": 2
}
```

说明：

1. 分段单位应以顶层 block 数量或 HTML 字节数为准，建议单段 `20-40` 个顶层块，或 `30-50KB html`。
2. `deliveryMode=full` 与 `deliveryMode=segmented` 必须并存，便于灰度与快速回滚。
3. 目录锚点若命中未加载段落，前端必须先补拉到目标 chunk，再执行滚动定位。

### Fallback 规则

1. 若 `rendered` 不存在、生成失败、版本不兼容，前端退回 legacy `ReadonlyPageEditor`。
2. 若单个交互块 hydrator 失败，只退回该块的占位或静态链接，不拖垮整页正文。
3. 若服务端静态渲染异常率超阈值，可整体关闭 flag，恢复 legacy 阅读路径。

## 缓存与性能策略

### 初期策略

1. 不新增数据库表。
2. 可按 `page.updatedAt` 或 `contentHash` 做内存 / Redis 级缓存。
3. 仅在渲染耗时确实成为瓶颈时，再讨论持久化缓存。
4. 长文档分段缓存优先按 `contentHash + segmentIndex` 组织，避免整文缓存和分段缓存相互污染。

### 不应过早做的事

1. 在未验证静态 HTML 保真前，就先做复杂持久化 cache 表。
2. 在未验证 `page-info` 响应尺寸与渲染耗时前，就先拆新接口。
3. 为了彻底去 QueryClient 而大改整个 share app；这属于补偿项，不是本期主路径。

## 模块改造点

| 模块 | 变更点 | 优先级 |
| --- | --- | --- |
| server share renderer | 新增分享安全 HTML 渲染服务，复用 `jsonToHtml` 能力 | P3 |
| server page-info | 扩展 `POST /shares/page-info` 响应结构，附带 `rendered`；静态 HTML 命中时裁剪 `page.content` | P3 / P4 |
| client shared-page | 新增 `SharedPageHtmlContent`，happy path 走 HTML 主渲染 | P3 |
| client hydrators | 针对 Drawio / Excalidraw / Embed 等建立单块 hydrator 注册表 | P3 |
| client toc/search | TOC 从 DOM 或 `rendered.toc` 生成；搜索保留 enhancement 层 | P3 |
| client reader theme | 移除分享页 palette/runtime theme，改为固定 Reader 样式 | P3 |
| client code block renderer | 代码块与 `Mermaid` 改为纯展示块，不再走 readonly node view | P3 |
| client fallback | 保留 legacy `ReadonlyPageEditor` 作为灰度与回滚兜底 | P3 |
| server/client segmented delivery | 超长文档补充 `headHtml + nextCursor` 与 chunk 续传 | P4 |

## 构建与灰度策略

1. 保持现有 share 独立 entry，不回退到主站入口。
2. 对静态 HTML 方案增加独立 feature flag，支持：
   - workspace 维度
   - shareId/pageId 白名单
   - 流量比例放量
3. 新旧两套正文渲染路径需并存一段时间，做到：
   - 分享域独立灰度
   - 问题出现时秒级回切
   - 不影响主站其他路由
