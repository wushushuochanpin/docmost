## 设计结论

**本需求在首期静态 HTML 阅读器落地时，不涉及新增或变更业务数据表、迁移或持久化 schema。**

## 当前建议

1. 分享页静态 HTML 渲染使用现有 `share`、`page`、`page.content` 数据，不新增业务主表字段。
2. `rendered.html / toc / interactiveBlocks / contentHash` 优先作为接口计算结果返回，不先写库。
3. 无需编写数据库迁移脚本，无需更新 `db.d.ts` 或 repo 层表结构。

## 可选缓存设计（非首期门槛）

### 方案 A：无持久化缓存

- 每次 `POST /shares/page-info` 读取 page content 后现场生成 HTML。
- 适用：渲染耗时可接受、灰度期需要快速迭代 renderer。

### 方案 B：内存 / Redis 派生缓存

- cache key 建议：`share-render:{pageId}:{contentHash}`
- 失效条件建议：
  - `page.updatedAt` 变化
  - `contentHash` 变化
  - rendererVersion 变化
- 适用：生成 HTML 的 CPU 成本可感知，但仍不值得引入数据库迁移。

### 方案 C：持久化缓存表

- 当前不建议首期引入。
- 仅在满足以下条件时考虑：
  1. 静态 renderer 已经稳定
  2. 渲染耗时成为后端主要瓶颈
  3. 内存 / Redis 缓存不足以支撑命中率和成本目标

## 数据一致性约束

1. `rendered.html` 是 `page.content` 的派生结果，不是新的业务数据源。
2. 任何缓存命中都必须以 `contentHash` 或等价版本号保证“正文 JSON 与 HTML 同版”。
3. 灰度期间保留 `page.content` 返回，用于 legacy fallback 和 diff 校验。
