## 背景与目标

### 背景问题

1. 分享页在移动端（微信内置浏览器、H5）打开缓慢，用户主观感受为白屏长、正文出现晚、操作不确定。
2. 第一轮优化已经解决了大量“明显不该首屏加载”的问题，但用户体感仍慢，说明当前瓶颈已经从“壳层太重”转向“正文阅读仍在启动编辑器”。
3. 真实核心诉求不是“保留所有能力且都首屏就绪”，而是“先让用户读到内容，再补齐辅助功能与少数交互块”。
4. 当前短文档体感已明显改善，但长文档仍慢，说明瓶颈已从“壳层过重”进一步收敛到“正文 payload 与整篇 HTML 一次性下发”。

### 代码审计证据（截至 2026-03-06）

1. 分享路由已拆成独立 share bootstrap，`/share/*` 不再走主站 `App` 的完整启动链路。
2. `SharedPage`、`ShareRedirect`、`ShareShell` 已完成 skeleton、首屏请求分层与辅助能力懒加载。
3. `ReadonlyPageEditor` 已不再复用编辑态全量扩展，改为 `readonly-extensions` 并按文档特征延迟装配节点能力。
4. 最近一次本地 build 统计显示，分享路径依赖闭包已降到约 `410 KB gzip`；但正常分享正文仍要挂载 `EditorProvider`、装配 TipTap 扩展并解析 JSON 文档。
5. 结论：继续只靠前端拆包，收益会快速递减。下一阶段的真正根因治理，是让“分享阅读页”不再默认启动 TipTap 只读运行时。
6. 当前 `POST /shares/page-info` 在静态 HTML 命中时，仍会把整份 `page.content` 与整份 `rendered.html` 一起返回；对长文档，这意味着正文被重复传输一次。

## 现状审计（As-Is，当前真实基线）

### 当前已完成的一阶段优化

1. 分享页已具备独立 share bootstrap，`/share/*` 首屏不再强依赖主站 `App`、主站埋点与主站布局装配。
2. `SharedPage` 与 `ShareRedirect` 已从空白 loading 改为 skeleton。
3. `ShareShell` 已将树、搜索、TOC 等能力改为按条件或懒加载。
4. 只读编辑器已切换到 `readonly-extensions`，并对 Drawio、Excalidraw、Embed、Mention 等做只读降级与动态装配。

### 当前仍存在的核心瓶颈

1. 正文仍通过 `ReadonlyPageEditor -> EditorProvider -> TipTap extensions` 渲染，本质仍是“启动一个编辑器来阅读内容”。
2. 即使扩展数量减少，浏览器仍要做 JSON 文档解析、schema 建立、节点实例化和 node view 装配，这对移动端 CPU 和内存不友好。
3. 一些共享基础包仍会进入分享阅读路径，继续靠拆包微调，收益边际已明显下降。
4. 目录和锚点目前仍依赖 editor state；这使分享页在产品定义上仍然被“编辑器运行时”绑住。
5. 分享页仍残留主题 / palette 运行时与本地存储同步逻辑。它不是当前最大性能瓶颈，但会扩大启动链和出错面，不符合“阅读页最小运行时”目标。

### 当前用户痛点的本质

1. 用户要的是“阅读一个公开页面”，不是“打开一个只读编辑器实例”。
2. 只要正文仍靠 TipTap 只读运行时来呈现，移动端就会持续承担与“阅读”不匹配的运行时成本。
3. 因此，下一阶段的主矛盾不是“再少几个 chunk”，而是“分享正文能否脱离编辑器实例”。

## 改造策略确认闸门

- current_stage：production（分享页已有真实流量）
- strategy：hybrid（迁移路径采用渐进式；当前代码为阶段一，目标架构为服务端静态 HTML 阅读输出）
- 决策理由：这是生产链路，不适合一次性切断旧阅读路径；需通过 feature flag 双轨并存，逐步验证渲染保真与安全。

## 能力复用与重复建设审查

- existing_scan：现有分享域（ShareLayout、SharedPage、share-query、Share API）继续复用业务语义；复用服务端现成 `jsonToHtml / generateHTML` 能力，不复用正文 TipTap 运行时作为最终阅读形态。
- build_vs_reuse：extend
- consolidation_plan：复用分享业务域与现有权限模型，替换正文渲染方式；“业务复用、阅读器替换”是本次改造原则。

## 已确认业务取舍

| 决策 ID | 已确认取舍 | 通俗解释 | 直接效果 |
| --- | --- | --- | --- |
| D1 | 重内容可先占位后加载 | 图表、嵌入卡片等先显示“加载中”或静态占位，不要求第一秒完整渲染 | 正文更早出现，手机端更快有内容 |
| D2 | 搜索 / TOC / 主题切换不阻塞首屏 | 这些能力仍保留，但正文出来后再补齐，或在用户点击时再加载 | 首屏 JS 和壳层装配更轻 |
| D3 | 分享页独立化 | `/share/*` 走独立 share app / entry，而不是继续完全挂在主站统一入口下 | 分享页可独立优化、灰度、回滚 |
| D4 | 分享正文默认不是“编辑器实例” | 正常分享正文页默认渲染静态 HTML，而不是启动 TipTap 只读编辑器 | 去掉阅读链路里大量无谓运行时 |
| D5 | 交互型块采用“静态占位 + 按需挂载” | Drawio、Excalidraw、Embed 等块只在出现或被交互时加载真正渲染器 | 保留能力，但不让它们绑架首屏 |
| D6 | 分享页不保留手动主题切换 | 一期采用固定 Reader 浅色主题，不加载 palette 同步、主题切换按钮和本地存储监听 | 减少运行时复杂度与分享专属 bug 面 |
| D7 | 代码块与 Mermaid 优先走纯展示 | 代码块是灰底纯展示区域；`Mermaid` 一期先展示源码块，不恢复客户端绘图运行时 | 保证可读、稳定和低成本，而不是勉强保留编辑器体验 |
| D8 | 长文档采用“先瘦首包，再按块渐进加载” | 不是按手机第一屏像素高度切内容，而是先返回最小正文首包，再按顶层 block / HTML 字节续传 | 对长文档有效，且工程边界稳定 |
| D9 | 阅读 affordance 不得被性能优化牺牲 | `details/切换块` 在纯展示模式下仍必须保留可见展开箭头；移动端目录抽屉点击条目后自动收起，桌面目录保持打开 | 快了以后仍像成熟阅读器，不让用户误判内容不可展开或目录“卡住” |

## 目标方案（To-Be）

### 总体产品方案

1. 分享页优先服务“阅读”而不是“编辑器能力齐备”。
2. 用户打开链接后，先看到 skeleton 与标题/正文，再渐进补齐树、搜索、TOC、主题与重内容渲染器。
3. 分享页拥有独立运行时；正常正文路径不再默认挂载 TipTap 只读运行时，而是渲染服务端生成的静态 HTML。
4. 长文档分阶段优化：先消除首包重复 payload，再在有证据的前提下引入块级渐进加载。

### 方案是什么（通俗解释）

1. 现在的分享页，本质是“先在浏览器里启动一个只读编辑器，再把文档内容画出来”。
2. 目标方案改成“服务端先把文档 JSON 生成一份安全 HTML，前端拿到后直接展示正文”。
3. 用户第一眼看到的是已经排好版的正文 HTML，不需要先等编辑器、扩展、节点视图全部准备好。
4. 只有 Drawio、Excalidraw、Embed、少数媒体预览等交互型块，才在进入视口或用户点击时补挂载专用渲染器。

### 用户感知差异

| 维度 | 当前阅读路径 | 静态 HTML 阅读路径 |
| --- | --- | --- |
| 首屏正文 | 依赖 TipTap 只读运行时准备完成 | 依赖 `page-info` 返回 HTML 即可展示 |
| JS 成本 | 需要编辑器 runtime、schema、node view | 仅保留轻量分享 runtime 与少数 hydrator |
| 重内容 | 即使延迟加载，仍受编辑器体系约束 | 静态占位 + 单块按需挂载 |
| 目录 | 基于 editor state 生成 | 基于 HTML 标题锚点或服务端 toc 数据 |
| 风险点 | 包体与 CPU 成本高 | 需要做好 HTML 保真、清洗与回退 |

### 内容分层策略

| 内容类型 | 目标渲染方式 | 首屏是否必须完整可用 | 说明 |
| --- | --- | --- | --- |
| 标题、段落、标题层级、列表、引用、链接 | 静态 HTML | 是 | 这是正文主体，必须直接可读 |
| 表格、Callout、Details、图片、附件 | 静态 HTML 或轻量 DOM 组件 | 是 | 以阅读为主，不依赖编辑器状态 |
| 代码块 | 静态 HTML 纯展示块 | 是 | 独立灰底容器、语言标识、等宽字体；复制能力如保留，必须是轻量原生增强 |
| Mermaid | 一期按纯展示代码块输出，二期可选服务端 SVG | 是 | 一期先保证源码可读和区域语义正确，不把 `mermaid runtime` 带回分享首屏 |
| Drawio、Excalidraw | 静态占位 + 按需挂载 viewer | 否 | 首屏只保证用户知道这里有图，不要求立即可交互 |
| Embed、重型媒体 | 静态预览 + 按需挂载 | 否 | 首屏避免启动 iframe / 预览 SDK |
| TOC、搜索 | enhancement 层 | 否 | 正文出来后补齐 |
| 主题 / 配色 | 固定 Reader 主题 | 是 | 一期不提供手动切换；如未来需要暗色，仅允许纯 CSS `prefers-color-scheme` |

### 长文档策略（新增）

1. 先处理**重复传输**：
   - 当 `rendered.html` 可用时，分享首包不再额外回传整份 `page.content`
   - `page` 对象收敛为分享阅读首屏必需字段
2. 再处理**整篇一次性下发**：
   - 对超长文档引入块级渐进加载，而不是按 viewport 像素高度切片
   - 首包返回 `headHtml + nextCursor` 或等价结构，保证标题与首段正文先可读
   - 余下 chunk 通过游标续传，并在 idle / 接近底部时自动补拉
3. 明确不采用“按第一屏像素高度切片”：
   - 服务端无法稳定知道用户 viewport
   - 同一文档在不同设备上的“第一屏”不一致
   - 以顶层 block 或 HTML 字节为分段单位，更利于缓存、回滚与锚点映射

### 优先级排序

1. **P0：正文优先**
   - skeleton
   - 首屏请求最少化
   - 壳层能力不再先于正文装配
2. **P1：阅读器减重**
   - `readonlyExtensions`
   - 重内容占位 + 按需加载
3. **P2：分享页独立化**
   - `/share/*` 使用独立 share entry / share app
   - 与主站构建、灰度和回滚链路解耦
4. **P3：静态 HTML 阅读器替代 TipTap**
   - 服务端返回 share-safe HTML
   - 前端以 HTML 为正文主渲染路径
   - 交互块单独 hydrate
5. **P4：长文档首包与续传优化**
   - 静态 HTML 命中时不再回传整份 `page.content`
   - 超长文档按顶层 block / HTML 字节分段，首包优先返回 `headHtml`
   - 客户端自动追加后续 chunk，不阻塞首段可读
6. **P5：补偿项**
   - 若 P4 后仍不达标，再评估接口聚合、cache、进一步裁剪 Query 层

### 具体体验定义

1. **首屏体感**
   - 打开分享链接后 1 秒内必须看到 skeleton 或标题正文，禁止长时间白屏。
2. **静态正文策略**
   - 正常分享正文路径先展示静态 HTML，不等待 TipTap 只读编辑器 ready。
   - 标题锚点、基础链接、图片、附件、简单表格和代码块在 HTML 渲染后即应可读。
   - 代码块不是 `editable=false` 的编辑器，而是纯展示阅读块；必须有明确区域边界，例如灰底、圆角、语言标识、等宽字体。
   - `details/切换块` 不是“隐藏原生 marker 的普通卡片”；必须保留可见展开箭头或等价 affordance，保证读者能立即判断这里可展开。
3. **重内容策略**
   - Drawio / Excalidraw：先显示“图表加载中”占位卡片，再按需加载 viewer
   - Embed：先显示轻量预览或占位，不阻塞正文
   - Mention：优先降级为普通链接展示，不引入 suggestion / 编辑态运行时
   - `Mermaid`：一期先以纯展示代码块输出源码，不在分享页首期恢复客户端图形运行时；若后续确需图形化，优先服务端 SVG
4. **辅助能力策略**
   - TOC：优先从 HTML 标题锚点或服务端 toc 数据生成
   - 搜索：点击后再加载，或在 idle 时预加载
   - 不提供手动主题切换：分享页一期使用固定 Reader 浅色主题，不保留 palette 同步和本地存储监听
   - 移动端 TOC 若以抽屉形式展示，点击目录项后应自动收起；桌面右侧目录作为常驻导航，不自动收起
5. **运行时策略**
   - 分享页与主站运行时分离；不要求独立域名，但要求独立入口、独立打包、独立灰度
   - TipTap 只读运行时保留为迁移期 fallback，不再是默认 happy path
6. **长文档交付策略**
   - 一期先收敛首包，只返回分享阅读所需的最小 page 视图与 `rendered` 数据
   - 二期对超长文档启用块级渐进加载：首包先给标题、首段正文和必要锚点，后续内容自动续传
   - 目录锚点若命中未加载段落，前端需先补拉对应 chunk 再滚动定位

### 非功能要求

1. 不改变分享链接 URL 形态与 SEO 行为（除加载方式外）。
2. 与现有公开 / 受限 / 密码 / 过期能力完全兼容。
3. 分享页可以独立灰度与回滚，不影响主站其他路由。
4. 优化后仍需保持公开分享、受限分享、多页树、TOC、分享内搜索等能力最终可用；分享页主题采用固定 Reader 样式，不再承诺手动切换。
5. 允许灰度期间“静态 HTML 路径”和“legacy 只读编辑器路径”并存，但必须可快速回切。

## 验收标准（摘要）

- ACC-001：移动端或 4G 模拟下，打开分享链接 1 秒内出现 skeleton 或正文。
- ACC-002：首个正文可读时间 P75 较优化前下降至少 40%。
- ACC-003：包含 Drawio / Excalidraw / Embed 的页面，正文先出现，重内容随后补齐，不得阻塞正文首屏。
- ACC-004：重内容占位文案与加载态明确，用户不会误判为内容丢失。
- ACC-005：TOC、搜索不阻塞正文，但正文出现后可正常使用。
- ACC-006：分享页所有既有功能与权限行为与优化前一致。
- ACC-007：分享页支持独立灰度与回滚，回滚后主站不受影响。
- ACC-013：正常分享正文路径默认渲染服务端生成的 `rendered.html`，不挂载 TipTap 只读运行时。
- ACC-014：静态 HTML 与 legacy 只读渲染在标题、正文层级、表格、代码块、图片、附件等内容上的展示差异可接受，无结构性缺失。
- ACC-015：静态 HTML 输出经服务端清洗，不能执行不受信脚本、事件处理器或危险协议链接。
- ACC-016：关闭静态 HTML 开关后，分享页可回切到 legacy 只读编辑器路径，业务与权限不受影响。
- ACC-017：分享页一期不提供手动主题切换，不加载 palette 同步、本地存储监听等主题运行时；Reader 主题保持稳定可读。
- ACC-018：代码块在分享页按纯展示块渲染，具备独立灰底区域与语言语义；`Mermaid` 一期按源码展示块渲染，不依赖客户端绘图 runtime。
- ACC-020：静态 HTML 命中时，`page-info` 响应不再额外回传整份 `page.content`，长文档首包冗余率为 0。
- ACC-021：超长文档启用块级渐进加载后，标题与首段正文先可读，后续 chunk 自动补齐；不得按 viewport 像素高度切片。
- ACC-023：`details/切换块` 在分享页纯展示模式下仍保留可见展开箭头或等价 affordance，用户不会误判为普通静态卡片。
- ACC-024：移动端 TOC 抽屉点击目录项后自动收起；桌面右侧目录点击目录项后保持打开。
