## 背景与目标

### 背景问题

1. 用户在 Web 端点击“分享”后，现在只能复制链接，缺少面向微信传播的清晰入口。
2. 如果产品直接写“分享到朋友圈”或“发给微信好友”，会制造错误预期，因为普通网页没有这个权限。
3. 用户真实需要的不是技术说明，而是一个简单闭环：从当前页面进入微信，再完成转发或朋友圈分享。

### 目标

1. 让用户在 Web 端一眼知道“怎么分享到微信”。
2. 桌面端优先走二维码路径，减少用户自行截图、复制、再找手机的心智负担。
3. 微信内浏览器不展示无意义二维码，而是直接引导用户使用微信原生分享菜单。
4. 手机非微信浏览器不误导用户，以复制链接为主。

## 现状审计（As-Is）

1. 现有分享弹窗位于文档页右上角 `Share` 入口，已支持：
   - 公开链接生成
   - 密码分享
   - 复制链接
   - 打开链接
2. 当前代码中没有：
   - 二维码生成与展示
   - 微信环境识别后的专属交互
   - 微信分享文案引导
3. 当前“复制链接”是可用的，但不是高频微信传播场景下的最好体验。

## 系统用户与角色

| 角色 | 目标 | 权限边界 | 场景 |
| --- | --- | --- | --- |
| 桌面端文档发送者 | 通过桌面浏览器把文档带到微信里 | 只能生成分享，不可替微信发送 | 办公场景、PC 浏览器 |
| 手机端微信用户 | 用微信原生能力转发好友或朋友圈 | 必须走微信原生菜单 | 微信内 H5 |
| 手机端非微信用户 | 先拿到链接，再进入微信传播 | 无法直接使用微信原生分享 | Safari / Chrome 等 |

## 已确认业务取舍

| 决策 ID | 已确认取舍 | 通俗解释 | 直接效果 |
| --- | --- | --- | --- |
| D1 | 按环境分流 | 同一个“分享”入口，在不同环境下展示不同下一步 | 用户不再被误导 |
| D2 | 桌面端展示二维码 | 这是桌面进入微信链路的主路径 | 用户知道接下来该扫码 |
| D3 | 微信内只做原生引导 | 不展示二维码，直接告诉用户点右上角菜单 | 交互符合微信习惯 |
| D4 | 手机非微信以复制链接为主 | 一部手机自己扫自己没有意义 | 避免无效交互 |
| D5 | 密码分享不主推二维码 | 扫码只带链接，不带密码 | 避免失败体验 |

## To-Be 产品定义

### 入口

1. 入口维持在文档页右上角现有 `Share / 分享` 按钮。
2. 不新增站外“微信分享专页”。
3. 分享弹窗在生成链接成功后，直接承载微信分享交互。

### 桌面浏览器交互

1. 用户点击右上角 `Share`
2. 弹出分享弹窗
3. 若当前为公开分享，则在链接区下方展示 `Share with WeChat` 面板
4. 面板中展示：
   - 二维码
   - 提示文案：`Scan this code with WeChat`
   - 下一步说明：`Open the page in WeChat and use the top-right menu to send to friends or share to Moments`
5. 继续保留 `Copy link`

### 微信内浏览器交互

1. 用户在微信内打开分享页后点击 `Share`
2. 弹窗中不展示二维码
3. 直接展示说明文案：
   - `Open the top-right menu in WeChat`
   - `Send to friends or share to Moments`

### 手机非微信浏览器交互

1. 用户在手机浏览器点击 `Share`
2. 弹窗中不展示二维码
3. 展示说明文案：
   - `Copy the link and paste it into WeChat`
4. 保留复制按钮

## 验收标准

- ACC-001：桌面浏览器中，公开分享链接生成后，分享弹窗内出现二维码和微信分享说明。
- ACC-002：桌面端二维码扫描后能打开当前分享页。
- ACC-003：微信内打开分享弹窗时不展示二维码，而是展示右上角原生分享引导。
- ACC-004：手机非微信浏览器中不展示二维码，而是引导复制链接。
- ACC-005：密码分享仍保持复制“链接 + 密码”能力，不新增误导性的二维码入口。
