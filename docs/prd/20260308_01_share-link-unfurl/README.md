## 需求确认结论

1. 目标不是让浏览器地址栏“自动显示成文档标题”，那不受业务控制；真正可控的是分享卡片预览与分享链接本身的可读性。
2. 本专题拆成两件事分别治理：
   - 分享卡片预览：让微信等渠道尽可能展示标题、摘要、图片，而不是一串链接。
   - 分享链接美观化：让裸链接本身保持规律、稳定、可读。
3. 微信是优先渠道，但必须承认平台边界：
   - 微信内打开网页后，可借助官方 JS-SDK 设置分享内容。
   - 聊天里直接粘贴链接后的卡片展示，仍受微信自己的抓取与展示策略控制，无法 100% 强制。
4. 公开分享允许展示真实标题与摘要；受限分享（密码/过期）不得在预览层泄露真实标题、正文摘要或封面。
5. 分享链接必须坚持“稳定 key 负责定位，slug 负责好看”，不能把标题本身变成唯一主键。

## 关键决策

1. 不把“链接好不好看”和“微信能否展示标题卡片”混为一谈；两者分别设计、分别验收。
2. 继续复用现有分享域与 share key 体系，不新造分享主键。
3. canonical 分享链接采用“短 key + 可读 slug”策略；slug 仅用于可读性和 SEO，不参与主定位。
4. 公开分享使用服务端注入的富预览元信息；受限分享只允许返回降级或泛化元信息。
5. 微信增强分为两层：
   - 服务端 HTML 预览元信息，服务于外部抓取与通用渠道。
   - 微信内 H5 菜单分享增强，服务于页面已在微信内打开后的二次分享。
6. 不承诺“所有微信聊天场景都一定显示标题卡片”；PRD 与对外表述均采用 best-effort 口径。

## 非目标

1. 不试图改变浏览器地址栏的基础展示规则。
2. 不把页面标题作为唯一 URL 主键，不支持纯标题 URL 直接定位页面。
3. 一期不提供用户自定义分享标题、摘要、封面图编辑能力。
4. 不为了微信单一平台，牺牲公开/受限分享的安全边界。
5. 一期不新增数据库表；若后续要做预览缓存，优先内存/Redis 或衍生接口，不先落库。
