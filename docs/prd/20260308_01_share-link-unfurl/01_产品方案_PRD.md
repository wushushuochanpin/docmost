## 背景与目标

### 背景问题

1. 用户的真实痛点不是“URL 里有字母”本身，而是别人收到分享后，看不出这是什么文档，也不知道值不值得点。
2. 当前分享链路已重点优化性能，但“分享出去后外部可理解性”仍弱：
   - 裸链接可读性一般。
   - 分享预览卡片能力不足。
   - 微信作为高频渠道，没有针对性定义支持边界。
3. 如果不把“分享卡片预览”和“美观稳定链接”分开治理，产品很容易陷入错误预期：
   - 错误预期 1：以为改 URL 就能保证微信一定显示标题卡片。
   - 错误预期 2：以为把标题放进链接就能取代稳定主键。

### 代码审计证据（As-Is）

1. 当前复制分享链接已带标题 slug，但仍使用旧分享路径：`/share/{shareKey}/p/{titleSlug}-{pageSlugId}`。实现位于 `apps/client/src/features/page/page.utils.ts`。
2. 当前分享 SEO 入口由 `apps/server/src/core/share/share-seo.controller.ts` 负责，已在首屏 HTML 中注入：
   - `<title>`
   - `og:title`
   - `twitter:title`
   - 可选 `robots=noindex`
3. 当前实现明确避免为密码分享泄露真实元信息；受限分享直接返回原始 `index.html`，不注入标题卡片元信息。
4. 当前系统没有：
   - `og:description`
   - `og:image`
   - `og:url`
   - `og:type`
   - `twitter:description`
   - `twitter:image`
   - `canonical`
   - 微信 JS-SDK 分享增强
5. `share.key` 已是 10 位小写字母数字短 key；`page.slugId` 已是 10 位大小写字母数字短 id，并非 UUID。说明“链接很长很乱”的主因，不是底层主键过长，而是缺少对外 canonical 规范与预览体验设计。

## 现状审计（As-Is）

### 当前分享链接现状

1. 已具备稳定 share key 和 page slug id，不需要新增一套分享主键。
2. 当前 URL 结构具备“标题 slug + 稳定 id”的基本思路，但对外路径仍偏技术化，且 legacy 路由并存。
3. 复制链路与 SEO 路由的 canonical 规则不够统一，用户很难形成“这个链接长什么样才是标准”的认知。

### 当前分享预览现状

1. 当前仅能稳定保证标题级元信息，不足以支撑较完整的卡片预览。
2. 对受限分享的保守处理是正确的，但产品层没有把“公开分享可展示、受限分享不泄露”明确定义成规则。
3. 当前没有单独定义“聊天里直接粘贴链接的预览”与“页面在微信内打开后的菜单分享”这两条链路。

### 微信支持边界（必须明确）

1. 微信官方 H5/JS-SDK 能力支持在微信内置浏览器里设置分享内容。
2. 微信 JS-SDK 提供 `updateAppMessageShareData`、`updateTimelineShareData` 等接口，适用于“页面已在微信内打开后”的菜单分享链路。
3. 但用户把链接直接粘贴到聊天会话后，最终是否展示卡片、展示成什么样，仍然取决于微信自己的抓取和展示规则，业务方无法 100% 强制。
4. 因此，本 PRD 采用双层目标：
   - 可控目标：服务端元信息 + canonical 链接 + 微信内二次分享配置。
   - 不可承诺目标：所有微信聊天场景都一定展示期望卡片。

## 已确认业务取舍

| 决策 ID | 已确认取舍 | 通俗解释 | 直接效果 |
| --- | --- | --- | --- |
| D1 | 不承诺地址栏显示为标题 | 地址栏永远是 URL，不能“自动变标题” | 避免错误产品预期 |
| D2 | 公开分享展示真实预览 | 标题、摘要、封面图可用于提升点击意愿 | 分享更像正式内容卡片 |
| D3 | 受限分享不泄露真实预览 | 密码/过期分享只能展示泛化或空元信息 | 守住隐私与安全边界 |
| D4 | 微信支持，但分层实现 | 微信内打开后的二次分享可做增强；聊天里直接粘贴链接是 best effort | 既利用平台能力，也不许诺做不到的事 |
| D5 | 链接采用“稳定 key + 可读 slug” | key 定位，slug 美观；slug 错了也能纠正 | 兼顾稳定与可读 |
| D6 | 复制链路只输出 canonical URL | 对外只给一套标准分享链接，不再把 legacy 路由暴露给用户 | 链接形态更统一 |

## To-Be 产品定义

### 产品定义 1：分享卡片预览

1. 公开分享：
   - 使用文档标题生成 `<title>`、`og:title`、`twitter:title`
   - 使用正文前若干可公开文本生成 `description`
   - 输出 `og:url`、`og:type`、`canonical`
   - 如可行，输出统一封面图或动态标题卡片图
2. 受限分享：
   - 不暴露真实标题、真实摘要、真实封面
   - 可选泛化标题，例如“受保护文档”
   - 仍保留 `noindex` 与必要的最小元信息

### 产品定义 2：canonical 分享链接

1. canonical 链接采用“短 key + 可读 slug”结构。
2. 标题 slug 仅用于可读性，不是定位主键。
3. 错误 slug、历史路由和 legacy 路由均应重定向到 canonical 版本。
4. 用户复制分享时，只返回 canonical 版本，避免外部传播多种路由形态。

### 产品定义 3：微信支持

1. 微信内打开分享页后，支持二次分享元信息增强。
2. 增强内容应与公开分享卡片元信息保持同源，不额外维护两套标题摘要。
3. 微信分享增强失败时，页面仍可正常浏览，退回服务端元信息方案。

## 验收标准

- ACC-001：公开分享页面首屏 HTML 包含完整的标题、摘要、URL、类型与基础社交卡片元信息。
- ACC-002：公开分享的复制链接与页面 canonical URL 一致。
- ACC-003：密码分享与过期分享不得泄露真实标题、真实摘要、真实封面图。
- ACC-004：`searchIndexing=false` 的分享仍注入 `robots=noindex`，但不影响正常分享传播。
- ACC-005：用户复制分享链接时，始终得到 canonical URL，而不是 legacy 路径。
- ACC-006：旧分享链接、错误 slug 链接、legacy `/share/p/:pageSlug` 链接仍可打开，并被重定向或纠正到 canonical URL。
- ACC-007：页面在微信内打开后，若微信能力配置齐全，则右上角菜单分享的标题、摘要、链接可被正确设置。
- ACC-008：微信或其他平台对直接粘贴链接的最终预览样式不做强制承诺，但公共分享应尽量通过服务端元信息提高成功率。
