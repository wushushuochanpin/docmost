## 背景

1. 当前系统只有“手动触发备份 + 查询作业 + 下载产物”的半成品能力，缺少自动调度、策略配置和恢复闭环。
2. 当前代码把 `workspaceId` 作为作业记录维度，但实际打包逻辑是整库 `pg_dump` 与整份存储复制，存在“展示为工作区备份、实际接近实例级打包”的语义错位。
3. 用户的真实核心诉求不是“多一个定时按钮”，而是“工作区管理员可以在当前工作区内自助配置、执行、查看、验证并恢复备份”。
4. 若不把“工作区级逻辑备份”和“实例级灾备”边界拆开，产品会向用户传递错误的可恢复预期，带来高风险事故。

## 关键决策

1. 本专题定义的是“工作区级自助备份/恢复”，不替代平台级全实例灾备。
2. 功能页面挂在当前工作区设置下，不在单页中切换多个工作区。
3. V1 每个工作区只允许 1 条自动备份策略，配置方式为“每日 / 每周 / 每月 + 固定时间 + 时区”，不开放原始 Cron。
4. V1 恢复只支持“恢复到新工作区”，明确拒绝原地覆盖当前工作区。
5. 备份产物默认落腾讯 COS（经现有 S3 兼容配置），本地下载只是分发方式，不是长期真源。
6. 手动与自动必须共用同一套作业状态机、审计字段和产物格式。

## 非目标

1. 不把本专题包装成“平台级灾备已完成”。
2. V1 不支持恢复到现有工作区，不支持差异合并。
3. V1 不支持原始 Cron、自定义多策略并发、增量备份、CDC 复制。
4. V1 不支持直接浏览任意 COS bucket/prefix 中的外部历史对象作为恢复源；恢复源限定为当前系统已记录的成功作业或用户手工上传的备份包。
5. V1 不恢复成员体系、认证配置、License、Billing、API Keys 和外部分享状态。

## 与历史方案关系

1. 历史目录 `docs/prd/periodic-backup-packaging` 更偏“实例级灾备打包”与整库/整存储快照。
2. 本专题重新定义为“工作区级逻辑备份/恢复产品能力”；两者的目标、产物格式、恢复语义与风险面不同，不应混用。
