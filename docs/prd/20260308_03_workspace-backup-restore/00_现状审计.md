### 审计结论摘要

1. 当前系统不是“完全没有备份”，而是“手动备份半闭环”。
2. 当前实现没有自动调度、没有策略配置、没有恢复能力、没有真正的工作区级导出语义。
3. 若直接在现有实现上增加 Cron，只会把“语义错位的手动打包”自动化，不能满足用户核心诉求。

## 页面与交互现状（As-Is）

### 已有页面

1. 已有 `Backup & Restore` 设置页，位于 `/settings/backup`。
2. 页面当前只提供：
   - “Run backup now”
   - “Cleanup stale jobs”
   - 备份作业列表
   - 成功任务下载
3. 页面没有：
   - 自动备份策略配置
   - 下次执行时间展示
   - 恢复入口
   - 恢复记录
   - 备份范围说明

### 现有页面问题

| 现状 | 问题本质 | 风险 |
| --- | --- | --- |
| 页面名是 `Backup & Restore` | 产品语言已承诺恢复，但功能并未闭环 | 用户认知被高估 |
| 只展示手动作业列表 | 没有策略状态、下次执行时间、保留策略信息 | 无法运维 |
| 没有 scope 提示 | 用户会默认以为是“当前工作区完整可恢复备份” | 语义误导 |

## 后端接口现状（As-Is）

### 已存在接口

1. `GET /backups/jobs`
2. `POST /backups/jobs/run`
3. `POST /backups/jobs/cleanup-stale`
4. `GET /backups/jobs/:id`
5. `GET /backups/jobs/:id/download-url`
6. `GET /backups/jobs/:id/download`

### 缺失接口

1. 无 `GET/PUT /backups/policy`
2. 无恢复 dry-run / apply 接口
3. 无恢复记录接口
4. 无上传备份包并发起恢复接口
5. 无“下次调度时间”查询接口

### 权限现状

1. 当前接口统一复用工作区设置管理权限：`WorkspaceCaslAction.Manage + WorkspaceCaslSubject.Settings`。
2. 这说明现有权限边界适合承载“当前工作区设置页”入口。
3. 也说明不应在单页里切换其他工作区，否则会把工作区设置权限与跨工作区运维权限混在一起。

## 数据模型现状（As-Is）

### 已落地的表

1. `backup_policies`
2. `backup_jobs`
3. `backup_restores`

### 已有但未闭环的字段

| 表 | 关键字段 | 当前问题 |
| --- | --- | --- |
| `backup_policies` | `cron_expr`, `timezone`, `retention_*`, `target_driver`, `target_config` | 表结构存在，但服务、接口、UI 未使用 |
| `backup_jobs` | `trigger_type`, `status`, `artifact_path`, `checksum`, `metadata` | 只用到了手动任务的一部分字段，`checksum` 未真正写入 |
| `backup_restores` | `mode`, `status`, `report` | 仅有表结构，没有执行链路 |

### 多租户可行性事实

1. 大多数核心内容表有 `workspace_id` 字段：
   - `spaces`
   - `pages`
   - `attachments`
   - `comments`
   - `page_history`
   - `shares`
2. 这为“按工作区做逻辑导出”提供了基础。
3. 但这不代表可以直接用整库 `pg_dump` 冒充工作区备份；逻辑导出仍需做数据白名单、身份映射与引用重写。

## 打包实现现状（As-Is）

### 当前真实执行逻辑

1. `BackupPackageService` 读取 `DATABASE_URL`，直接执行整库 `pg_dump`。
2. 当 `STORAGE_DRIVER=local` 时，复制本地文件目录。
3. 生成 `manifest.json` 与压缩包，记录到 `backup_jobs`。

### 当前实现与目标诉求的偏差

| 当前行为 | 与目标诉求的偏差 | 结论 |
| --- | --- | --- |
| 整库 `pg_dump` | 不是工作区级备份 | 不能直接复用为 V1 工作区备份格式 |
| 仅在 `local` 模式复制文件 | 对 COS/S3 文件无真实快照能力 | 与用户已确认的 COS 方案不匹配 |
| `artifactPath` 带 `workspaceId` 目录 | 目录看起来像工作区级，但内容不是 | 存在高误导风险 |
| `checksum` 字段未落值 | 不能做完整性校验 | 不满足可恢复要求 |

## 调度与状态现状（As-Is）

1. 当前备份模块没有调度器。
2. 项目虽然已接入 `@nestjs/schedule`，但备份模块未使用。
3. 目前只有“手动触发 -> 队列执行 -> 查询状态”的链路。
4. stale job 清理是人工入口，不是自动巡检闭环。

## 对象存储与下载现状（As-Is）

### 已具备能力

1. `StorageService` 已支持：
   - 上传
   - 流式上传
   - 读取
   - 读取流
   - 生成签名下载 URL
2. `S3Driver` 基于 AWS S3 SDK，可兼容腾讯 COS。

### 当前不足

1. 现有存储抽象没有对象列表查询接口，但对 V1 并非硬阻塞。
2. 因为工作区恢复源可限定为“系统已记录的成功作业”或“用户上传的备份包”，并不需要在页面上任意浏览 bucket。

## 恢复能力现状（As-Is）

1. 没有备份恢复 API。
2. 没有恢复 worker。
3. 没有 dry-run 校验。
4. 没有恢复记录页。
5. 没有“新工作区恢复”的数据映射方案。

## 现状能力复用评估

| 能力 | 当前状态 | 建议 |
| --- | --- | --- |
| 任务状态机与队列 | 可复用 | 继续扩展 `backup_jobs` 与 `backup_restores` |
| COS/S3 上传与签名下载 | 可复用 | 作为备份产物主存储 |
| 设置页入口与工作区权限 | 可复用 | 继续挂在当前工作区设置内 |
| 当前 `pg_dump` 打包逻辑 | 不可直接复用为工作区备份语义 | 保留给未来平台级灾备，V1 不继续扩展 |
| Import 上传链路 | 可局部复用 | 复用 multipart 上传与临时文件处理模式 |

## 已知差距清单

1. 产品边界未定义：工作区级 vs 实例级。
2. 页面语义过宽：写了 Restore 但没有恢复能力。
3. 备份范围不透明：当前记录维度与真实打包范围不一致。
4. COS 场景未打通：当前仅 local 文件复制。
5. 调度缺失：没有自动策略闭环。
6. 恢复缺失：没有 dry-run、apply、报告、回滚策略。
7. 安全边界未收敛：若未来直接做原地覆盖恢复，风险极高。

## 结论

1. 本需求不能被定义为“给现有手动备份加一个定时器”。
2. 正确方向是：在现有工作区设置入口、任务表与存储抽象上扩展，新增“工作区级逻辑快照 + 恢复到新工作区”的独立产品能力。
3. 现有整库 `pg_dump` 路径不应再被包装成工作区备份；它最多保留为未来“平台级灾备”能力的技术资产。
