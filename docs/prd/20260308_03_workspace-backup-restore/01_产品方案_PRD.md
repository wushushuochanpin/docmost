## 背景与目标

### 背景问题

1. 当前系统备份需要人工触发，无法满足“最多丢 24 小时数据”的基本 RPO 目标。
2. 当前页面虽名为“Backup & Restore”，但没有恢复闭环，产品承诺与真实能力不一致。
3. 当前备份作业按 `workspaceId` 记账，却实际走整库/整存储打包，存在语义错位。
4. 用户真正需要的是“当前工作区可以自助配置自动备份、查看结果、做恢复验证，并在需要时恢复到一个安全的新工作区”。

### 设计理念与决策记录

| 方案 | 描述 | 优点 | 核心问题 | 结论 |
| --- | --- | --- | --- | --- |
| A | 延续当前整库打包，只增加自动调度 | 开发最快 | 语义错误，不能称为工作区备份；恢复风险不受控 | 拒绝 |
| B | 工作区级逻辑快照，恢复到新工作区 | 语义清晰、风险可控、适合自助化 | 需要做 ID 映射与格式设计 | 采纳 |
| C | 工作区级逻辑快照，直接覆盖当前工作区 | 用户操作路径最短 | 写入风险最高，误恢复不可逆 | V1 拒绝，未来再评估 |

补充原则：

1. `全量备份` 不等于“新备份覆盖旧备份”。每一份全量备份都是独立快照，具备独立恢复价值。
2. 历史备份是否保留，应该由 retention 策略和受限的手动删除共同决定，而不是默认认定“前序备份没用”。

## 系统用户与角色

| 角色 | 目标 | 权限边界 | 高风险动作 |
| --- | --- | --- | --- |
| Workspace Owner / Admin | 配置自动备份、手动触发、查看作业、发起恢复 | 仅限当前工作区，不可跨工作区操作 | 发起正式恢复 |
| 运维 / SRE | 监控失败任务、验证恢复能力、处理异常 | 具备实例运维能力，但不应绕过产品边界把工作区备份当实例灾备 | 处理失败恢复、容量告警 |
| 安全 / 合规负责人 | 审核备份访问、确认下载与恢复留痕 | 以审计和策略为主，不直接修改业务内容 | 下载审批、恢复审计复核 |

## 现状审计（As-Is）

1. 前端只有手动运行、清理 stale job、下载成功产物。
2. 后端已有 `backup_jobs` 手动作业链路，没有策略管理和恢复。
3. 数据库有 `backup_policies`、`backup_restores` 表，但未被产品能力使用。
4. 当前实现不能安全满足“工作区级自动备份 + 可恢复”目标。

## 改造策略确认闸门

- current_stage：production
- strategy：hybrid
- user_confirmation：confirmed
- 决策理由与回退约束：
  - 生产环境已有手动备份作业链路，不适合一次性推翻所有实现。
  - 复用现有入口、作业状态机与存储抽象，但重新定义工作区级产物格式与恢复语义。
  - 若新恢复链路异常，可关闭恢复入口，仅保留手动/自动备份与下载，不影响现有业务写链路。

## 产品范围（To-Be）

### 页面入口与信息架构

1. 页面入口：当前工作区设置 `Settings > Backup & Restore`。
2. 页面范围：仅显示当前工作区的数据，不提供页面内跨工作区切换。
3. 页面结构：
   - 概览卡片：最近成功备份、下次执行时间、目标存储、保留策略
   - 自动备份策略：启停、频率、时间、时区、保留份数/天数
   - 手动备份：立即备份
   - 备份作业列表：状态、时间、大小、触发方式、错误、下载、发起恢复
   - 恢复面板：选择成功作业或上传备份包，先 dry-run 后 apply
   - 恢复记录列表：状态、目标工作区、报告摘要

### 恢复按钮交互定义

1. 备份作业列表中的“恢复”按钮不是一键恢复，也不是点击后立即创建工作区。
2. “恢复”按钮只作为恢复流程入口，只对 `success` 作业展示。
3. 点击后打开恢复抽屉或弹窗，并预选当前作业作为恢复源。
4. 恢复向导的顺序必须是：
   - 输入目标工作区名称
   - 查看恢复范围与排除项
   - 先执行 dry-run
   - 查看 dry-run 报告
   - 二次确认后再执行正式恢复
5. 只有在用户点击正式确认后，系统才自动创建一个新工作区并把备份内容恢复进去。
6. 若用户关闭弹窗或 dry-run 未通过，不得创建新工作区。

### V1 必做范围

1. 工作区级自动备份策略：
   - 每个工作区最多 1 条策略
   - 频率只支持：每日 / 每周 / 每月
   - 用户只配置固定时间和时区，不配置 Cron 表达式
2. 工作区级手动备份：
   - 与自动任务共用同一状态机和作业列表
3. 备份产物管理：
   - 默认存腾讯 COS
   - 成功作业支持本地下载
   - 自动 retention 负责常规清理
   - 支持受限的手动删除历史备份产物
4. 恢复能力：
   - 支持从成功作业恢复
   - 支持上传本地备份包再恢复
   - 必须先 dry-run，再允许正式恢复
   - 正式恢复只允许恢复到新工作区
5. 状态与审计：
   - 备份与恢复记录在后端可查
   - 手动/自动状态、错误摘要、触发方式展示一致

### 历史备份删除策略

1. 应增加“删除历史备份产物”能力，但它不是主清理机制，主机制仍然是 retention。
2. 删除对象是“备份产物”，不是“备份记录”；删除后作业记录仍然保留，状态可查、审计可查。
3. V1 删除规则：
   - 仅允许删除 `success` 的历史备份
   - 不允许删除当前工作区最后一份可用的成功备份
   - 不允许删除正在被 dry-run / apply 使用的备份
   - 删除后该记录不可再下载、不可再恢复
4. 页面交互建议：
   - 在作业行的更多操作菜单中提供“删除备份”
   - 不是主按钮
   - 二次确认文案必须提示“删除后将无法下载或恢复该备份”

### V1 明确不做

1. 不支持恢复到当前工作区
2. 不支持自由 Cron
3. 不支持增量/差异备份
4. 不支持恢复成员体系、邀请、认证配置、API keys、License、Billing
5. 不支持自动重新激活外部分享链接

### 备份范围定义

#### V1 纳入备份

1. 工作区基础元信息：
   - 名称
   - 描述
   - 非敏感设置快照
2. 内容域数据：
   - spaces
   - pages
   - page history
   - attachments 元数据与对象内容
   - comments
   - backlinks
3. 恢复报告与统计摘要

#### V1 不纳入备份

1. 用户与认证域：
   - users
   - auth providers
   - workspace invitations
   - MFA / API keys
2. 商业与运维域：
   - billing
   - license
   - telemetry
3. 高风险外部访问域：
   - public shares 的原始访问状态
   - 旧密码保护配置

### 恢复结果定义

1. 恢复完成后生成一个新工作区。
2. 新工作区默认由本次操作人担任 Owner/Admin。
3. 原工作区保持不变，旧数据不被覆盖。
4. 恢复报告明确列出：
   - 成功恢复的数据域
   - 被跳过的数据域
   - 用户映射/降级情况
   - 警告与错误

## 非功能要求

1. 默认 RPO 目标：`<= 24h`。
2. 备份与恢复均为异步任务，不阻塞页面请求。
3. 同一工作区同一时间最多 1 个备份任务运行。
4. 同一工作区同一时间最多 1 个恢复任务运行。
5. 下载链接必须为短时效签名 URL 或等价临时授权。
6. 恢复前必须有二次确认，并展示“将创建新工作区，不覆盖当前工作区”。

## 验收标准

- ACC-WBR-001：管理员可在当前工作区设置页保存 1 条自动备份策略，策略字段包含频率、固定时间、时区、保留规则。
- ACC-WBR-002：策略启用后，24 小时内至少按计划触发 1 次自动备份，作业列表可见 `triggerType=schedule`。
- ACC-WBR-003：点击“立即备份”后，列表立即出现 `pending` 或 `running` 任务，后续状态更新为终态。
- ACC-WBR-004：手动与自动任务在列表中使用同一组状态、错误摘要、大小、触发方式展示规则。
- ACC-WBR-005：恢复操作必须先执行 dry-run；未通过 dry-run 不允许正式恢复。
- ACC-WBR-006：正式恢复成功后生成新工作区，原工作区内容保持不变。
- ACC-WBR-007：成功作业落 COS，可生成有效下载链接并下载到本地。
- ACC-WBR-008：页面与帮助文案必须明确“这是工作区级备份，不等同实例级灾备”。
- ACC-WBR-009：V1 恢复结果中不应自动激活历史公开分享、认证配置、邀请和 API keys。
- ACC-WBR-010：后端可按工作区查询备份作业与恢复记录，记录包含状态、开始/结束时间、错误摘要、操作人和目标工作区。
- ACC-WBR-011：作业列表中的“恢复”按钮必须先进入恢复向导；只有通过 dry-run 且用户二次确认后，系统才自动创建新工作区并执行恢复。
- ACC-WBR-012：系统支持对历史成功备份执行受限删除；删除后记录仍保留在后端可查，但该备份不可再下载或恢复，且最后一份可用成功备份不可删除。
