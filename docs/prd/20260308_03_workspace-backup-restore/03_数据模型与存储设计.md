# 03 数据模型与存储设计

**成文日期**：2026-03-08 13:41:35 UTC+8
**最后修订**：2026-03-08 18:37:30 UTC+8

本文档用于定义核心实体、字段与存储策略。阅读时当前系统实现可能已发生变化，请以实际代码与产品行为为准，谨慎参考。

---

## 设计目标

1. 让 `backup_policies`、`backup_jobs`、`backup_restores` 真正承载工作区级备份/恢复产品能力。
2. 让产物格式天然表达“逻辑快照”，而不是隐式依赖底层数据库实现。
3. 让恢复报告可读、可追溯、可审计。

## 数据表设计

### 1. `backup_policies`

#### 现状

已有字段：

- `workspace_id`
- `cron_expr`
- `timezone`
- `retention_days`
- `retention_count`
- `target_driver`
- `target_config`
- `last_run_at`

#### 建议调整

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schedule_kind` | text | `daily | weekly | monthly`，作为用户意图的真实来源 |
| `schedule_config` | jsonb | 结构化时间配置，如 `{"hour":2,"minute":0}` |
| `next_run_at` | timestamptz | 调度器扫描依据 |
| `last_success_at` | timestamptz | 概览卡片和告警依据 |
| `last_failure_at` | timestamptz | 告警依据 |

#### 索引建议

1. `unique index backup_policies_workspace_id_uq (workspace_id)`
2. `index backup_policies_enabled_next_run_at_idx (enabled, next_run_at)`

#### 设计说明

1. 保留 `cron_expr`，但它退化为调度执行层衍生值，不再由前端直接编辑。
2. `schedule_kind + schedule_config` 是产品配置的真实语义层。

### 2. `backup_jobs`

#### 保留字段

1. `trigger_type`
2. `triggered_by_user_id`
3. `status`
4. `artifact_path`
5. `artifact_size_bytes`
6. `checksum`
7. `error_code`
8. `error_message`
9. `metadata`

#### 建议扩展

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `scope_type` | text | 固定为 `workspace`，为后续实例级灾备保留区分 |
| `artifact_driver` | text | `s3 | local`，避免策略变更后难以定位历史产物 |
| `package_format_version` | integer | 用于恢复兼容性判断 |
| `artifact_deleted_at` | timestamptz | 产物被手动或自动清理的时间 |
| `artifact_deleted_by_user_id` | uuid | 手动删除操作者；自动 retention 可为空 |
| `artifact_delete_reason` | text | `manual_cleanup | retention_cleanup | system_cleanup` |

#### `metadata` 建议结构

```json
{
  "policySnapshot": {
    "scheduleKind": "daily",
    "timezone": "Asia/Shanghai",
    "retentionDays": 30,
    "retentionCount": 30
  },
  "summary": {
    "spaces": 3,
    "pages": 128,
    "attachments": 412,
    "comments": 56,
    "totalAttachmentBytes": 987654321
  },
  "includedDomains": [
    "workspace",
    "spaces",
    "pages",
    "page_history",
    "attachments",
    "comments",
    "backlinks"
  ],
  "excludedDomains": [
    "memberships",
    "auth",
    "shares",
    "api_keys",
    "billing"
  ]
}
```

#### 设计说明

1. 不建议物理删除 `backup_jobs` 记录。
2. 历史可查与状态一致的前提，是“记录保留、产物删除”。

### 3. `backup_restores`

#### 建议扩展

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `source_type` | text | `job | upload` |
| `source_job_id` | uuid | 当来源为成功作业时使用 |
| `source_upload_id` | uuid / text | 复用 `file_tasks.id` |
| `target_workspace_name` | text | 目标新工作区名 |
| `target_workspace_id` | uuid | apply 成功后写入 |
| `dry_run_token` | text | 约束 apply 必须依赖成功 dry-run |

#### `report` 建议结构

```json
{
  "packageFormatVersion": 1,
  "warnings": [
    "shares are skipped in v1",
    "2 users could not be mapped and were downgraded to operator/null"
  ],
  "summary": {
    "spaces": 3,
    "pages": 128,
    "attachments": 412,
    "comments": 56
  },
  "mapping": {
    "usersMatched": 8,
    "usersMissing": 2
  }
}
```

## 复用现有文件上传表

### `file_tasks`

1. 上传恢复包不建议再造新表。
2. 建议复用 `file_tasks`：
   - `type = backup-restore-upload`
   - `status = uploaded | validated | expired`
   - `filePath` 指向临时产物存储位置

### 优点

1. 复用现有上传权限与存储能力
2. 避免新增一次性临时表
3. 清理逻辑可与导入临时文件统一治理

## 备份产物存储设计

### COS / Local 路径约定

#### COS（推荐）

```text
backups/workspaces/{workspaceId}/{yyyy}/{MM}/{jobId}.tar.gz
```

#### Local（兼容）

```text
{BACKUP_LOCAL_PATH}/workspaces/{workspaceId}/{yyyy}/{MM}/{jobId}.tar.gz
```

### 说明

1. `artifact_path` 统一存储“相对 key/path”。
2. 真正的 driver 与 bucket/prefix 来自 `artifact_driver + target_config`。
3. 当 `artifact_deleted_at` 非空时，该产物不再可下载、不再可恢复。

## 逻辑快照包格式

### 目录结构

```text
workspace-backup-{workspaceId}-{timestamp}.tar.gz
  manifest.json
  summary.json
  checksums/SHA256SUMS
  data/workspace.json
  data/spaces.ndjson
  data/pages.ndjson
  data/page-history.ndjson
  data/comments.ndjson
  data/backlinks.ndjson
  data/attachments.ndjson
  data/actors.ndjson
  files/<attachment-id>/<original-file>
```

### `manifest.json` 最小字段

| 字段 | 说明 |
| --- | --- |
| `scopeType` | 固定为 `workspace` |
| `packageFormatVersion` | V1 固定 `1` |
| `createdAt` | 备份创建时间 |
| `sourceWorkspaceId` | 来源工作区 |
| `docmostVersion` | 产物创建时应用版本 |
| `storageDriver` | 业务文件原始存储驱动 |
| `artifactDriver` | 备份产物当前存储驱动 |
| `includedDomains` | 已纳入数据域 |
| `excludedDomains` | 已排除数据域 |
| `summary` | 统计摘要 |

## 纳入与排除的数据域

### V1 纳入

| 数据域 | 来源表 / 来源对象 | 说明 |
| --- | --- | --- |
| 工作区壳层 | `workspaces`（白名单字段） | 仅恢复非敏感元信息 |
| 空间 | `spaces` | 恢复空间结构 |
| 页面 | `pages` | 恢复内容与层级 |
| 历史版本 | `page_history` | 恢复历史快照 |
| 附件 | `attachments` + 存储对象 | 同时导出元数据与二进制 |
| 评论 | `comments` | 恢复评论内容 |
| 反链 | `backlinks` | 恢复内容引用关系 |

### V1 排除

| 数据域 | 原因 |
| --- | --- |
| `users` / `auth_*` | 身份属于实例级资源，不应由工作区备份克隆 |
| `workspace_invitations` | 过期与安全语义复杂 |
| `shares` | 公开链接与密码保护属于高风险外部访问面 |
| `groups` / `group_users` / `space_members` | 需要复杂的跨环境身份映射，V1 暂不恢复 |
| `api_keys` / `billing` / `license` | 明确属于实例级或商业域 |
| `watchers` / `notifications` | 非核心恢复域，可后续评估 |

## ID 映射策略

### 原则

1. 因为恢复目标是“新工作区”，所以不能复用源工作区的实体 UUID。
2. 恢复过程必须对以下 ID 做重映射：
   - `workspaceId`
   - `spaceId`
   - `pageId`
   - `attachmentId`
   - `commentId`

### 映射产物

1. 运行中使用内存或临时 KV 保存 `sourceId -> targetId`
2. 最终在 `backup_restores.report` 中输出摘要，而不是完整公开映射表

## 用户引用映射策略

### V1 规则

1. 备份包中导出引用到的 actor 信息快照，仅包含：
   - `sourceUserId`
   - `email`
   - `name`
2. 恢复时按 email 尝试匹配当前实例已有用户
3. 未匹配成功时：
   - 对非必填用户字段写 `null`
   - 对必需责任人字段回落为当前操作人
4. 报告中明确列出映射结果与降级数量

## 数据迁移与回滚

### 新增 / 改造表策略

1. 以加字段、加索引为主，不删除现有字段。
2. 旧作业数据不回填为新格式，只标记为 legacy。
3. 若上线后关闭新能力：
   - 保留新增字段与表
   - 停止调度、隐藏 UI
   - 不删除已生成产物
