# PRD 书写规范（Skill）

将自然语言需求转为**可结构化解析、可评审、可落地开发与测试**的“机器友好 PRD”。核心：把说明性文本升级为可计算的结构化字段，并在**页面 ↔ 接口 ↔ 数据表 ↔ 权限 ↔ 埋点**之间建立一一对应映射。

本 skill 为**一个入口、多方向详述**：主文说明用途与总则，各方向完整模板与 Checklist 见 **references** 下对应文件，**不要精简内容**，按需查阅。

## 何时使用本 Skill

- 撰写新 PRD 或把需求整理成 PRD 时。
- 评审 PRD 是否具备“可读、可实现、可验证”三要素时。
- 需要统一 PRD 目录结构、决策记录、章节写作要点时。
- 撰写前端逐页、后端接口、数据表与迁移、权限与安全、测试与验收、或机器可读格式与 AI Prompt 时，按方向查阅下方 reference 文件。

## 适用范围与角色矩阵

- **适用**：功能较完整的业务模块，尤其多角色协作的中后台/运营系统。
- **角色-关注点**（建议在 PRD 头部固定）：
  - 产品：需求边界、目标指标、功能拆解、决策依据、验收标准、上线灰度与兜底。
  - 设计：页面入口、信息架构、交互规则、状态/异常/空态、组件复用、无障碍与响应式。
  - 前端：逐页字段（列/筛选/排序/操作）、接口契约、错误处理、埋点、权限控制点。
  - 后端：职责分解、接口设计、幂等/事务/一致性、权限校验、性能与限流、数据迁移与回滚。
  - 测试：功能/接口/权限/安全测试点、回归范围、验收用例与门槛。
  - 数据：埋点与日志粒度、宽表/汇总表口径、指标定义与观测、历史兼容。

## 六项写作 Skill（硬约束）

生成或评审 PRD 时，以下六项必须满足：

- **Skill A：从入口到容错**。写清入口路径、入口带参、参数缺失处理、重试阈值、告警与兜底；UI 交互与后端容错绑定（如短时重复点击 → 后端幂等校验）。
- **Skill B：把“成本/风险”显式写成策略**。如灰度走后端配置、灰度维度（比例/用户/地区/标签）与生效方式。
- **Skill C：每个关键链路都有可量化指标**。OKR/KR 级写关联准确率、延迟、覆盖率等，并说明如何观测。
- **Skill D：页面级规则写到字段粒度**。列表筛选项、默认值、时间范围、表头显示/自定义、hover、提示文案、权限过滤提示，用表格逐项枚举。
- **Skill E：数据记录先定粒度/主键/字段含义/必传**。埋点与日志表写清记录粒度、字段表、必传/选传、样例值。
- **Skill F：变更可追溯**。修改日志、评审纪要、决策理由可回溯。

## 新增：需求澄清 + 现状能力优先（硬约束）

对“改造类需求”必须先澄清“需求问题”再讨论“实现方案”；必须先完成 As-Is 与复用评估，再写 To-Be；禁止跳过现状直接写目标方案。

### 工作流（按顺序执行）

1. 需求澄清闸门（Problem First）：先向需求方确认“为什么做、解决什么问题、当前损失是什么、成功指标是什么（口径+目标值+时间窗）”；未澄清前不得锁定方案。
2. 现状审计（As-Is）：盘点现有页面、交互、接口、数据表、权限、埋点、开关与发布方式。
3. Build vs Reuse 决策：评估“复用 / 扩展 / 新建”三选一并与需求方确认；若现状能力或可控扩展可满足，默认不新建能力。
4. 改造策略确认（Replace / Migrate / Hybrid）：明确是否生产、外部依赖、数据迁移可逆性、双写双读与灰度约束。
5. 判定档位（small / medium / large）：按风险与影响面优先，不按文档数量。
6. 影响面矩阵：逐项写清“现状行为 -> 改造后行为 -> 影响对象 -> 风险等级 -> 回归范围”。
7. 目标方案（To-Be）：输出页面、接口、数据、权限、测试与验收。
8. 灰度与回滚：灰度维度、放量节奏、监控指标、回滚触发条件与执行步骤。

### 档位与产物最小要求

- small：允许单文档 PRD（不强制整套多文档）；必须包含现状审计、影响面、测试回归、回滚方案。
- medium：建议专题包（README + 01~06），用于跨前后端/跨系统且存在接口或字段变更。
- large：建议扩展包（含 00/07/08/09），用于中台化、跨域架构改造或高合规/高可用风险场景。

信息不足时默认 medium；若发现破坏式变更、跨系统联动或租户/权限边界调整，自动升级档位。

## 新增：PRD 新建与存储规范（硬约束）

PRD 文档必须存储在 `docs/prd/` 下，统一命名，保证可检索、可归档、可追溯。

### 存储位置与命名规则

1. 新建 PRD 包默认使用目录，不建议在根目录散落多个无关联文件。
2. 目录命名规范：`{YYYYMMDD}_{index}_{short_slug}`。
3. `short_slug` 要求：
   - 语义精准、简短，建议 2-5 个词；
   - 仅允许小写字母、数字、短横线（`[a-z0-9-]`）；
   - 长度建议不超过 32；
   - 禁止使用 `new`、`final`、`v2`、`测试` 等无业务语义名称。
4. 单文件例外仅限 small 且同时满足：单团队、无跨系统、无数据迁移、无灰度发布。
5. PRD 标题与目录名必须可互相映射，避免“文档名和功能名不一致”。

### 存储质量检查（评审硬门槛）

- 路径不在 `docs/prd/`：不通过。
- 命名不符合规范：不通过。
- 目录名过长或语义不清：不通过。
- 同一功能出现多个重复命名目录：不通过。

## 新增：改造策略确认闸门（硬约束）

凡涉及“推翻或改动当前方案”，必须先与需求方确认策略：是“兼容过渡”还是“直接重构”。

### 策略分类与默认建议

1. 直接重构（Replace）
- 适用：0->1 阶段、尚未生产投产、无真实用户数据负担、无外部依赖约束。
- 特点：简化历史包袱，快速收敛到目标架构。

2. 兼容过渡（Migrate with Compatibility）
- 适用：已发布生产、存在真实用户流量、存在外部调用或存量数据。
- 特点：双轨兼容、灰度切换、可回滚。

3. 局部替换 + 兼容壳（Hybrid）
- 适用：核心链路需重构但外围依赖暂不能同时升级。
- 特点：内部重构，外部接口短期保持兼容。

### 必须确认的决策项

- 当前是否已生产发布。
- 是否存在外部系统依赖/下游调用。
- 是否存在不可逆数据迁移。
- 是否允许短期双写/双读。
- 是否允许分阶段灰度。
- 选择 Replace / Migrate / Hybrid 的理由。

### 强制规则

1. 未完成“策略确认”前，不得输出最终实施方案，只能输出候选方案与待确认问题清单。
2. 若判定为已生产场景，默认走兼容过渡；若要直接重构，必须有明确确认记录与回退预案。
3. 任何“直接推翻生产链路”的方案，必须附带停机影响评估、回滚时长、演练计划。

## 新增：相同或类似功能禁止重复建设（硬约束）

相同或高度相似功能不允许重复建设；默认“复用优先、扩展次之、新建最后”。

### 重复建设判定（命中任意 1 条即进入审查）

1. 业务目标一致，差异仅为字段、文案或少量规则。
2. 页面形态一致（列表/详情/编辑）且交互流程高度重合。
3. 接口能力一致，仅参数组合不同。
4. 数据模型一致，仅状态或枚举扩展。

### 必填审查输出

1. Existing Scan：现有页面/接口/数据表/权限点扫描结果。
2. Build vs Reuse 结论：复用 / 扩展 / 新建（三选一）。
3. 若选择新建，必须给：
   - 与现有能力不重叠的边界定义；
   - 不复用的量化理由（性能/隔离/合规/演进）；
   - 未来收敛计划（避免长期并行两套能力）。

### 强制规则

- 无 Existing Scan，不进入评审通过。
- 无 Build vs Reuse 结论，不进入开发排期。
- 被判定为重复建设且无正当理由，方案退回重写。

## 新增：共享数据库场景处理（硬约束）

当线上与测试环境共用同一数据库时，PRD 必须先写“隔离与发布安全”，再写功能细节。

### 触发条件（命中任一即启用）

1. 线上与测试共用同一 DB 实例或同一 schema。
2. 测试服务可访问生产 workspace 数据。
3. 改造包含写链路、迁移、批量操作。

### 强制规则（AI 输出必须包含）

1. 隔离优先：先定义写入隔离策略（如 workspace release channel + 后端 guard），再定义功能上线。
2. 变更最小化：数据层默认“只增不改”（新增表/字段优先），禁止先做破坏式 DDL。
3. 灰度最小单元：按 workspace 灰度，不允许按“整库”一刀切。
4. 迁移可逆：迁移任务必须有任务表、明细表、幂等键、可回滚步骤。
5. 默认无影响：未命中灰度开关的 workspace 行为必须与线上现状一致。
6. 验收门槛：明确“跨环境误写入=0、回滚SLO、迁移成功率、关键错误率阈值”。

### 最小输出模板（可直接用于 PRD）

- shared_db_mode：true/false
- isolation_strategy：release_channel_guard / workspace_allowlist / schema_guard
- ddl_policy：additive_only / destructive_with_window
- rollout_unit：workspace
- migration_plan：job_based + reversible
- rollback_slo：<= 30min
- no_impact_scope：未开启 feature flag 的 workspace

## 必选章节目录与设计理念（摘要）

PRD 必选目录需覆盖：档位与产物策略、现状审计（As-Is）、设计理念、功能概述、菜单入口、权限矩阵、前端逐页、后端实现、数据表、接口契约、测试要点、验收标准、改造影响矩阵、迁移兼容、灰度灾备、修改日志。

设计理念写成可复用决策记录（PRD 内嵌轻量 ADR），字段包括：设计目标、痛点证据、方案集合（至少 2 个）、对比维度、决策理由、权衡与代价、成功指标（口径+目标值+数据来源+观测频率）、约束指标。

## 内置脚本（scripts）

本 skill 内置 PRD 包脚本，统一服务于 `docs/prd`：

1. `scripts/next_prd_index.sh [docs_prd_path] [yyyymmdd]`
2. `scripts/init_prd_package.sh <feature_name> [small|medium|large] [docs_prd_path]`
3. `scripts/validate_prd_package.sh [--legacy] <target_path> [small|medium|large|auto]`

说明：

- 脚本默认并强约束落盘到 `docs/prd`。
- 命名按 `YYYYMMDD_index_short-slug`（slug 仅 `a-z0-9-`，建议 2-5 词，长度 <= 32）。
- 校验脚本会检查：命名、目录结构、时间戳与免责声明、核心章节与回滚相关内容。
- `--legacy` 模式仅放宽历史命名问题（如下划线、超长 slug）为告警，不会放宽结构与内容门槛。
